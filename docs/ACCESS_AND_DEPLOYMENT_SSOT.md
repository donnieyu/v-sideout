## 1. 목적과 이 문서의 권위

기존 배구 모임 회원 20~30명이 새 서비스에 쉽게 들어와 본인 계정으로 참가 신청하도록 한다. 기존 회원은 마스터가 미리 등록하여 가입 신청을 다시 하지 않는다. 새로 들어오는 미등록 사용자에게만 승인형 가입 신청을 제공한다.

이 문서는 회원 접근, 계정 발급·관리, 공개 URL 배포의 단일 기준이다. 다른 세션은 동일 내용을 별도 기획서에 복제하지 말고 이 문서에 연결한다. 사용자 확정 요구, 제안 기본값, 미결정 사항, 실제 구현 상태를 구분한다. 사용자 최신 지시가 최우선이며 변경 시 본문과 변경 이력을 함께 수정한다.

- 기존 [회원·운영자 계정 등록 계획](MEMBER_ADMIN_PLAN.md)의 소속·모임별 권한 규칙을 아래에 승계한다. 기존 문서는 역사와 화면 맥락의 참고 자료로 보존한다.
- [제품 계획](PRODUCT_PLAN.md), [운영 앱 제품 기록](../web/PRODUCT.md)의 이전 회원 발급·배포 설명과 충돌하면 **이 문서의 확정 요구**를 우선한다. 제안을 구현 완료로 해석하지 않는다.
- 회차별 참가 신청·취소·팀편성 정책은 이 문서가 재정의하지 않는다. [참가 명단 SSOT 구현 인계](design-review/shadcn-prototype/ROSTER_SSOT_IMPLEMENTATION_HANDOFF.md)와 그 영역의 최신 사용자 결정을 따른다.
- 구현 진척은 [회원 개발 로드맵](MEMBER_ACCESS_IMPLEMENTATION_ROADMAP.md), [기존 인증 재사용 검토](reviews/MEMBER_AUTH_REUSE_REVIEW_2026-09-29.md), [인증 기반 보완 계획](superpowers/plans/2026-09-29-member-auth-foundation.md), [Task 1·2 인계](reviews/MEMBER_AUTH_TASK1_2_HANDOFF_2026-09-29.md), [Task 3 인계](reviews/MEMBER_AUTH_TASK3_HANDOFF_2026-09-30.md), [Task 4 인계](reviews/MEMBER_AUTH_TASK4_HANDOFF_2026-09-30.md), [M2 인계](reviews/MEMBER_MANAGEMENT_M2_HANDOFF_2026-09-30.md), [M3 화면 인계](reviews/MEMBER_ACCESS_M3_UI_HANDOFF_2026-09-30.md)를 따른다. 담당 간 연결은 [통합 계획](INTEGRATION_PLAN.md) 9절을 함께 읽는다.
- 설계 문서 생성은 외부 계정 생성, 요금제 결제, 실회원 자료 수집·업로드, 이메일 발송, 서비스 공개가 실행되었다는 뜻이 아니다.

## 2. 사용자 확정 요구

| ID | 요구 | 근거와 경계 |
| --- | --- | --- |
| U01 | 초기 실제 사용자는 20~30명 | 대규모 공개 가입 서비스로 확대하여 설계하지 않는다. |
| U02 | 닉네임·비밀번호 로그인 | 아이디는 소속 모임에서 쓰는 한글 또는 영어 닉네임·이름. 소셜 로그인을 필수로 하지 않는다. |

| U04 | 기존 회원에게 임시 비밀번호 제공 | 사이트 링크와 계정 정보를 전달받으면 로그인할 수 있어야 한다. 초대 링크 설정만 가능한 방식으로 대체하지 않는다. |
| U05 | 첫 로그인 때 모든 회원에게 비밀번호 변경 제공 | 2026-09-29 정정: 전달받은 임시 비밀번호를 그대로 계속 사용할 수 없는 규칙 유지. 이후에도 본인 비밀번호 변경 기능을 제공한다. |
| U06 | 미등록 사용자에게 로그인 페이지의 가입 신청 제공 | 신청만으로 로그인 가능한 계정이 생성되는 공개 회원가입은 지원하지 않는다. |
| U07 | 신규 신청 최소 정보는 닉네임·이메일·소속 모임 | 이메일은 가입 결과·임시 비밀번호 안내 및 공지 수신 목적. 비밀번호는 신청서에서 받지 않는다. |
| U08 | 신규 신청은 마스터가 승인 | 사용자 최초 요청은 승인 후 임시 비밀번호 안내다. 비밀번호 설정 링크는 대안 제안이며 확정된 대체 요구가 아니다. |
| U09 | 인터넷에서 접근 가능한 URL 제공, 비용 최소화 | 공개 URL과 회원 데이터 공개는 별개다. 로그인 전에는 회원 명단·운영 정보에 접근할 수 없어야 한다. |
| U10 | 다른 세션과 병행 가능한 개발 경계와 공유 기록 | 별도 세션 생성이나 상대 세션에 메시지 전송을 자동으로 수행하지 않는다. |
| U11 | 소속 모임 선택지에 `무소속` 포함 | 신규 가입 신청서와 마스터 회원 등록/수정 화면에 명시적으로 제공. 실제 모임 선택을 모든 일반 회원에게 강제하지 않는다. |
| U12 | 한글·영문 로그인 아이디 모두 중간 공백 불허 | 공백을 몰래 제거해 다른 아이디로 등록하지 않는다. 앞뒤 공백 정리·대소문자 비교·정규화는 P04 참고. |
| U13 | 비밀번호 구성 규칙은 최소 길이와 영문·숫자 조합 | 생일 등 추측 가능한 의미값의 금지 규칙은 제거. 특수문자 필수·대소문자 혼합 필수·의미 기반 차단을 추가하지 않는다. 2026-09-29 후속 응답에서 최소 8자로 확정. 임시 비밀번호를 그대로 유지할 수 없다는 규칙은 별도 유지. |
| U14 | 마스터가 채택한 로그인 아이디를 임시 비밀번호 발급 시 등록·점유 | 신규 신청의 닉네임이 중복되면 마스터가 최종 아이디를 정한다. 만료 시점까지 다른 사람에게 같은 아이디를 발급할 수 없으며, 중복 승인으로 서로 다른 임시 비밀번호가 발송되어서는 안 된다. 상세 수명주기는 6절 참고. |
| U15 | 비활성 계정도 기존 로그인 아이디와 고유성을 유지 | 내부 고유 회원 ID와 로그인 아이디를 매핑하더라도 로그인 아이디 자체에 서비스 전체 유일성을 보장한다. 다른 모임·활성화 대기·비활성 계정도 중복 검사에 포함한다. |

**2026-09-29 후속 정책 확정:** 사용자가 ‘제안한 기준으로 진행’을 선택하여 비밀번호 최소 **8자·영문과 숫자 포함**, 임시 비밀번호 **발급 시점부터 7일 유효**, **미활성 계정도 만료만으로 아이디를 자동 반환하지 않음**을 채택했다. 다른 제안 전체의 일괄 승인을 뜻하지 않는다.

이전 대화에서 제안된 ‘모든 기존 회원이 이메일 설정 링크를 거쳐야 한다’는 흐름은 U03·U04에 맞지 않으므로 기본안으로 채택하지 않는다.

## 4. 화면과 이용 흐름

### 4.1 기존 회원 — 기본 출시 경로

마스터 사전 등록 → 고유 로그인 아이디 확정·회원마다 다른 임시 비밀번호 발급 → 기존 연락 채널로 URL·확정 로그인 아이디·임시 비밀번호 개별 전달 → 로그인 → 본인 비밀번호 변경 → 일정·참가 신청.

- 최초 변경 화면은 새 비밀번호와 확인 입력에 집중한다. 이메일·프로필 완성을 동시에 강제하지 않는다.
- 20~30명 등록은 수동 입력 또는 보유 파일 가져오기 중 자료 형식을 보고 정한다. 파일 업로드는 아직 구현 요구로 확정하지 않았다.
- 가져오기를 선택하면 저장 전 미리보기, 중복·소속 매핑 확인, 재실행 시 계정·이력 중복 방지, 기존 비밀번호 임의 초기화 방지가 필요하다.
- 임시 비밀번호 평문은 계정 전달 순간에만 취급한다. 저장소·로그·일반 회원 목록·공유 문서에 남기거나 기존 비밀번호를 조회하는 기능을 만들지 않는다.
- 생일 등 특정 의미값이라는 이유로 비밀번호를 거절하지 않는다. 임시 비밀번호의 계속 사용 금지와 최소 길이·영문/숫자 구성 조건은 그대로 적용한다.

### 4.2 로그인·첫 비밀번호 변경

- 로그인 페이지: 닉네임, 비밀번호, 로그인 버튼을 주 행동으로 표시. 가입 신청·비밀번호 도움은 보조 링크.
- 임시 인증 상태에서 허용되는 동작은 비밀번호 변경·로그아웃 등 계정 활성화에 필요한 최소 동작뿐이다.
- 변경 완료 이후 일반 세션을 발급/회전하고 업무 접근을 허용한다. 변경 실패나 탭 재접속으로 우회되지 않아야 한다.
- 새 비밀번호는 최소 길이와 영문·숫자 포함 조건을 검사하고, 현재 임시 비밀번호와 동일하면 거절한다. 특수문자는 필수도 금지도 아니며 영문 대문자·소문자의 동시 사용을 강제하지 않는다. 확정 최소 길이는 8자이며 서버와 UI가 같은 정책값을 사용한다.
- 일반 회원·운영자·회장·마스터 모두 같은 최초 변경 규칙을 적용한다. 최초 마스터 생성은 서버의 별도 초기 설정 절차로 수행하고 공개 API에서 마스터를 생성하지 않는다.

### 4.3 신규 사용자 — 승인형 가입 신청

로그인 페이지의 가입 신청 → 닉네임/이름·이메일·소속(무소속 포함) 선택 → 접수 안내 → 마스터 검토·로그인 아이디 채택 → 승인·아이디 점유·임시 비밀번호 발급 또는 거절 → 확정 아이디와 임시 비밀번호 안내 → 첫 로그인·비밀번호 변경.

- 접수 문구: ‘가입 신청이 접수되었습니다. 승인되면 이메일로 안내해 드립니다.’
- 승인 전에는 로그인·명단 열람·참가 신청 권한이 없다. 신청 소속은 계정 소속 확정값과 구분한다.
- 신청 이력은 `대기 → 승인 / 거절`. 승인된 계정의 `활성화 대기 / 활성 / 비활성` 및 `메일 대기 / 발송 요청 성공 / 실패`는 별도 상태로 관리한다.
- 이메일 발송 요청 성공을 실제 수신·계정 활성화로 표시하지 않는다. 발송 실패 시 계정을 중복 생성하지 않고 재시도한다.
- 신청 닉네임은 희망값이며 접수만으로 로그인 아이디를 소유하지 않는다. 신청 닉네임이 중복되어도 별도 사람의 신청을 자동 병합하지 않고, 승인 시 마스터가 사용 가능한 로그인 아이디를 채택한다.
- 한 신청의 중복 승인으로 계정이 늘어나지 않고, 서로 다른 두 신청에 같은 로그인 아이디가 배정되지 않도록 서버와 DB에서 보장한다. 충돌한 쪽에는 임시 비밀번호를 발급·발송하지 않는다.
- 신청서에는 수집 목적을 짧게 설명한다. 신청·재발송 횟수를 제한하고 다른 신청자의 정보가 드러나지 않도록 한다.

### 4.4 마스터 회원 관리

첫 개발 범위는 회원 목록·검색·필터, 사전 등록, 계정 상세 수정, 신청 승인/거절, 임시 비밀번호 재발급, 비활성화/재활성화다. 이메일을 사용하면 발송 상태·재발송도 제공한다.

- 목록 표시: 신청 닉네임/표시 이름, 확정 로그인 아이디, 소속, 역할, 계정 상태, 최초 비밀번호 변경 여부, 임시 자격 만료·전달/메일 상태. 내부 ID와 연결하되 비밀번호·세션·인증 토큰은 표시하지 않는다.
- 회원 소속은 하나 또는 무소속이며 마스터만 지정/변경한다. 마스터는 소속 없음(`homeClubId=null`)으로 모든 모임을 관리한다.
- 운영자의 단일 소속 모임 기본 운영 권한과 추가 모임 권한을 구분한다. 일반 회원은 소속만으로 운영 권한을 얻지 않는다.
- 회장과 추가 운영진의 대리 신청·예외 배정 권한 차이를 유지한다. 하나의 `isAdmin` 값으로 통합하지 않는다.
- 모든 계정 관리 명령은 서버에서 마스터 권한을 검사한다. 비밀번호 재발급·권한 변경·비활성화는 행위자·대상·시각을 기록하되 자격 증명은 기록하지 않는다.
- 마지막 활성 마스터를 실수로 비활성화하거나 강등하여 관리가 불가능해지는 상황을 방지한다.
- 비활성화·재활성화는 같은 내부 회원 ID와 로그인 아이디를 유지한다. 비활성 계정을 신규 가입 대상으로 재생성하거나 그 아이디를 새 회원에게 넘기지 않는다.

### 4.5 비밀번호 분실과 이메일

- 이메일 없는 회원: 마스터가 기존 모임 연락 경로로 본인을 확인하고 임시 비밀번호 재발급. 재로그인 때 다시 변경한다.
- 검증된 이메일이 있는 회원: 일회용 재설정 링크 방식 권장. 가입 신청 이메일 입력만으로 검증 완료라고 표시하지 않는다.
- 재설정 요청만으로 현재 계정을 잠그지 않는다. 설정 완료 시 기존 세션을 폐기하고, 계정 존재 여부를 노출하지 않는 응답과 요청 제한을 적용한다.
- 공지 이메일은 서비스 운영 공지로 한정한다. 첫 출시에서 공지 작성·일괄 발송 UI까지 개발할지는 아직 미결정이다.
- 사전 등록 회원에게 이메일 등록을 강제하는 근거로 신규 신청서의 이메일 필수를 사용하지 않는다.

## 6. 로그인 아이디 소유권·임시 비밀번호 발급

### 6.1 식별자와 중복 검사

신청 닉네임/표시 이름, 확정 로그인 아이디, 내부 고유 회원 ID를 구분한다. 로그인 아이디는 내부 ID에 매핑되는 것과 별개로 서비스 전체에서 유일해야 한다. 활성 계정만을 대상으로 한 조건부 중복 검사는 허용하지 않는다.

- 한글·영문 아이디 내부의 일반 공백·탭·줄바꿈 등 공백 문자를 허용하지 않는다. `배구 왕`, `Volley Ball`을 `배구왕`, `VolleyBall`로 자동 합쳐 등록하지 않고 수정하도록 안내한다.
- 앞뒤 공백 제거, 영문 소문자 비교키, 한글 NFC 정규화 제안을 채택하면 등록·승인·로그인·아이디 변경·중복 확인에서 같은 함수를 사용하고 그 비교키에 DB 고유 제약을 둔다.

### 6.2 발급과 만료의 수명주기

| 상태/사건 | 로그인 아이디 소유권 | 임시 비밀번호 |
| --- | --- | --- |
| 가입 신청 대기 | 희망 닉네임만 접수, 아직 아이디 점유 없음 | 발급 없음 |
| 마스터 승인·발급 확정 | 마스터 채택 아이디를 특정 내부 회원 ID에 원자적으로 등록·점유. 다른 신청에 발급 불가 | 한 발급 건에 하나의 유효 임시 자격만 생성 |

| 활성/비활성 계정 | 임시 자격 만료와 관계없이 기존 아이디 고유성과 소유자 매핑 유지 | 비활성 계정은 유효한 비밀번호가 있어도 로그인 불가 |

임시 자격 만료는 발급 시점부터 **7일**로 사용자 확정되었다. 미활성 계정도 만료만으로 아이디를 자동 반환하지 않는다. 명시적 회수·삭제 절차는 별도 정책이며 현재 구현하지 않는다. **임시 비밀번호 만료를 이유로 활성·비활성 회원의 아이디를 반환하는 로직은 만들지 않는다.**

### 6.3 중복 발급·발송 방지 계약

1. 승인 시점에 신청 상태와 확정 아이디를 다시 검사한다. 화면의 ‘사용 가능’ 표시는 최종 보장이 아니다.
2. 아이디 고유 제약, 신청 1건당 계정/최초 발급 1건 제약, 승인·소유권·자격 버전·발송 작업 등록을 하나의 원자적 처리로 설계한다. 성공이 확정되기 전 메일을 보내지 않는다.
3. 같은 승인 요청의 재시도는 기존 처리 결과를 반환한다. 새 임시 비밀번호를 생성하지 않는다. 서로 다른 신청이 같은 아이디를 동시에 요구하면 하나만 성공한다.
4. 발송 작업은 발급 건을 식별하는 중복 방지 키를 사용한다. 단순 네트워크 재시도를 비밀번호 재발급으로 처리하지 않는다. 명시적 재발급만 이전 자격을 폐기하고 새 버전을 만든다.
5. 발송 전 계정·소유권·발급 버전·만료를 다시 확인하고 취소되었거나 교체된 발급 건은 발송하지 않는다. 재발급과 발송의 동시 처리 방법은 구현 계획에서 정의한다.
6. 외부 이메일 전달을 정확히 한 번으로 보장한다고 주장하지 않는다. 전달 결과가 불명확해도 두 계정에 같은 아이디가 생기거나 같은 계정에 서로 다른 유효 임시 비밀번호 두 개가 생겨서는 안 된다. 이미 보낸 과거 비밀번호는 회수할 수 없어도 재발급 후 사용할 수 없어야 한다.

메일 재시도에 필요한 자격 전달 방식·단기 보호 저장/폐기는 구현 계획에서 정한다. 평문 임시 비밀번호를 일반 DB 필드·로그·공유 문서에 영구 보관하는 방식은 사용하지 않는다.

검증 결과는 날짜, 대상 경로/커밋, 명령·브라우저 조건, 통과/실패, 미검증 범위를 기록한다. 목업 검사 통과를 서버 인증·운영 배포 검증으로 대체하지 않는다.

### 다음 작업 — 현재 회원·인증 세션

1. I는 서버 운영 모임 ID 원본과 `ClubDirectory.exists` 제공자를 연결한다. 제공자가 없거나 장애일 때 모임 지정은 503으로 거절하고, 없는 모임 ID는 400으로 거절한다. 업무 진입점은 C01–C04 계약대로 `active`만 허용한다.
2. A는 [M3 화면 인계](reviews/MEMBER_ACCESS_M3_UI_HANDOFF_2026-09-30.md)의 컴포넌트·클라이언트를 I에 넘기고 운영 최초 마스터 설정 절차를 별도로 준비한다. I는 공개/보호 라우트, 운영 모임 선택지, 내부 라우트/뒤로가기 미저장 guard를 연결한 뒤 합성·실제 계정 경계를 검증한다.
3. 신규 신청·승인·메일(M4), 업무 API 통합·원격 D1·제한 시험(M5–M6)을 거쳐 공개 URL 배포로 이동한다. 요금/도메인 후보는 실제 선택 시 재확인한다.

> 이 프로젝트에 회원·인증 개발과 참가 신청·팀편성 개발을 연결하는 **통합 담당 전용 채팅을 새로 만들어줘**. 프로젝트 경로는 `/Users/donnieyu/DevSource/Personal/v-team-builder`야. 새 담당은 `docs/ACCESS_AND_DEPLOYMENT_SSOT.md` v0.2 이상과 `docs/design-review/shadcn-prototype/ROSTER_SSOT_IMPLEMENTATION_HANDOFF.md`, 각 개발 세션의 최신 인계를 먼저 읽어야 해.
>
> 회원·인증은 ‘배포 및 운영 전략 세우기’ 채팅(`01a0e806-3863-76d1-bfa3-f34e3016e9ae`), 참가·팀편성은 ‘Plan Seoul volleyball club site’ 채팅(`01a0c686-ac70-7ca0-84b9-fddd9c11af09`)에서 진행 중인 범위와 실제 완료 상태를 확인해줘. 이 두 채팅과 새 통합 담당 사이에서 작업 범위·진척·통합 계약을 확인하고 인계 메시지를 주고받는 것을 허용해. 이 허용은 계정 발급·이메일 발송·실회원 자료 업로드·공개 배포 실행까지 포함하지 않아.

>
> 먼저 양쪽에서 주고받을 타입/API와 파일 담당표, 미완료 의존성, 통합 순서와 검증 기준을 정리해줘. 회원 SSOT의 사용자 확정 규칙을 따라 무소속 선택, 공백 없는 로그인 아이디, 비활성 계정까지 포함한 아이디 고유성, 마스터의 아이디 채택·단일 임시 자격 발급을 보존해. 기능이 준비되기 전에는 강제로 합치지 말고 목업 결과와 실제 인증·저장·배포 검증을 구분해.
>
> 루트와 `docs/`는 현재 Git 관리 밖이고 `web/`만 별도 저장소라는 점을 확인해. 기존 미커밋 작업을 이동·덮어쓰거나 루트에 임의로 Git을 초기화하지 마. 회원 SSOT는 복제하지 말고 참조하고, 계약·담당 변경은 문서 담당과 조율하여 반영해. 우선 통합 준비 현황과 작업 계획을 보고해줘.

### 다른 세션에서 이어갈 때 사용할 시작문

> `docs/ACCESS_AND_DEPLOYMENT_SSOT.md`를 먼저 읽고 회원 접근·계정 관리·공개 배포 작업을 이어간다. 확정 요구와 제안/미결정을 구분한다. 기존 회원 20~30명은 마스터 사전 등록과 개별 임시 비밀번호로 바로 로그인하며 가입 신청을 다시 하지 않는다. 가입 신청은 미등록 신규 사용자만을 위한 마스터 승인 절차다. `docs/design-review/shadcn-prototype/`의 참가 명단·팀편성 작업 상태를 먼저 확인하고 공유 파일을 동시에 수정하지 않는다. 실제 인증·서버 저장·이메일 발송·공개 배포의 완료 상태를 목업 완료와 구분한다. 결정과 진척은 이 SSOT에 갱신하고, 실제 개인정보·자격 증명을 문서나 저장소에 기록하지 않는다.
