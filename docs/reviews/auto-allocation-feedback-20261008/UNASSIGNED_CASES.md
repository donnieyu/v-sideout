# 자동 배치 후 미배정 사유 전수 검토

2026-10-08 · promotion-p1 · 기준 커밋 06418b7

후속 구현·검증은 [IMPLEMENTATION.md](IMPLEMENTATION.md)에 기록했다. 아래 ‘이번에는 수정하지 않았다’는 표현은 이 분석을 작성하던 시점의 상태다.

범위: 현재 자동 배치 알고리즘, UI 실행 경로, 자리 수 정책, 회원 자격, 수동 편집·저장 경계. 앱 코드와 실제 신청·저장 데이터는 수정하지 않았다. 정상 데이터 모델의 분기 검토이며 모든 손상 데이터·동시성 시나리오를 실증한 것은 아니다.

## 결론과 현재 설계 방향

성공적으로 실행된 자동 배치에서 활성 신청자가 남는 정상 조건은 **주포지션 미등록** 또는 **가용 자리 부족**이다. 주·부 포지션이 해당 자리와 다르다는 이유만으로 남기지 않는다. 주→부→기타 순서와 기본 자리 우선 배정은 유지한다. 이전 REVIEW.md의 일치 포지션만 우선 배정하고 운영자에게 마무리를 맡기는 대안은 현재 권장안이 아니다.

별도로 **다른 팀 삭제 후 자동 배치가 아무 일 없이 종료되는 UI 상태 결함**을 실제 컴포넌트 조작 테스트로 재현했다. 이것은 정상 미배정 사유와 구분하여 수정해야 한다.

## 정상 미배정과 복합 상황

| 조건 | 실제 동작 | 적절한 설명/처리 |
|---|---|---|
| 주포지션 미등록 | 빈자리가 있어도 자동 배치에서 제외 | 주포지션 미등록 N명. 프로필 등록 또는 수동 배정 경로 안내 |
| 신청자보다 전체 자리 수가 적음 | 수용 가능한 만큼만 배정 | 빈자리 부족 N명. 추가 선수 줄/팀 추가 또는 기존 배정 조정 |
| 추가 줄을 수동 삭제·조정함 | 수동 자리 수를 유지하므로 신청자가 늘어도 자동 확장을 보장하지 않음 | 용량 부족의 발생 경위로 설명. 자동으로 사용자의 삭제를 되돌리지 않음 |
| 수동 자리 수 유지 상태에서 팀 삭제·신청자 증가 | 줄 수가 같아도 전체 수용 인원이 줄거나 필요한 인원이 증가 | 동일한 용량 부족 범주 |
| 기존 기본 자리에 대기자·미신청 회원이 있음 | 기존 배정을 보존하므로 활성 신청자를 위한 자리가 부족할 수 있음 | 용량 부족 + 기존 배정 인원 설명. 기존 사람을 임의로 밀어내지 않음 |
| 유지가 허용된 기존 비활성 회원이 자리를 사용 | 그 자리는 새 신청자에게 사용할 수 없음 | 용량 부족의 점유 배경. 비활성 회원을 신규 후보로 제시하지 않음 |
| 미등록 신청자 + 대기자가 함께 있음 | 미등록 신청자를 건너뛰고 등록된 대기자가 빈자리를 채울 수 있음 | 전체 타일이 찼어도 신청자 완료로 표시하면 안 됨. 미등록과 점유 상황을 함께 설명 |
| 미등록과 자리 부족이 함께 있음 | 둘 이상의 조건이 중첩될 수 있음 | 사람별 대표 사유는 미등록을 우선하고 중복 집계하지 않음. 용량 상황은 별도 요약 |

정상 자동 용량 상태에서는 18명/3팀은 18자리, 21명은 21자리, 28명/3팀은 30자리로 맞출 수 있다. 따라서 ‘18명 초과’ 자체는 실패 원인이 아니다. 28명이 배정된 뒤 2자리가 남는 것도 정상이다. 수용 인원은 활성 신청자 수로 계산하므로 별도로 유지한 비신청자 배정까지 항상 보장하는 것은 아니다.

미등록 신청자보다 대기자를 먼저 완료시키는 현재 결과는 코드상 의도된 자격 필터의 결과지만, 운영자에게 혼란을 줄 수 있다. 이번 검토에서는 자동 대기자 편입 정책을 바꾸지 않았다. 사유 보기에서 빠진 신청자와 배정된 대기자를 구분해야 한다.

## 미배정 사유로 안내하면 안 되는 조건

- 전원이 OH 또는 S여도 등록된 활성 신청자는 빈 기본/추가 자리에 배정된다. 특정 포지션 지원자 부족, 주부 중복, 상대 포지션 불일치는 잔여 사유가 아니다.
- 부포지션만 없는 입력도 알고리즘은 배정한다. 이는 알고리즘 진단용 입력이며 현재 실제 프로필 API가 이 부분 상태를 허용한다는 뜻이 아니다.
- 이름/모임 검색, 후보 탭, 미신청 회원 필터, 코트/행 전환은 자동 배치에 전달되는 전체 후보를 필터링하지 않는다.
- 미신청 회원은 자동 배치 대상이 아니다. 그 회원들이 남아 있어도 신청자 미배정으로 세지 않는다.
- 미배정 비활성 회원은 자동 후보와 활성 신청자 잔여 수에서 제외한다. 기존 공개 배정 유지 규칙은 별도다.
- 대기자는 신청자와 다른 집단이다. 모든 신청자가 이미 배정된 UI에서는 대기자만 남았다고 자동 실행을 계속하지 않으므로 신청자 완료와 대기자 잔여를 구분한다.
- 모든 신청자를 배정했더라도 빈 팀/팀 수 등 공개 조건이 충족되지 않을 수 있다. 배정 완료와 공개 가능을 같은 조건으로 계산하지 않는다.

## 실행·저장 실패와 분리

공개 중 읽기 전용, 저장 처리 중, 최신 리비전 재확인 필요, 권한 부족, API 오류는 선수의 포지션 사유가 아니라 작업 실행·저장 조건이다. 데이터 조회 오류를 ‘프로필 미등록’으로 대체해서는 안 된다.

프로필만 바뀌고 편성/신청 리비전이 그대로일 때 편집 화면의 후보 정보가 최신으로 갱신되는지는 별도 통합 검증이 필요하다. 현재 후보 갱신 경로에 리비전 조기 반환이 있어 오래된 프로필을 사용할 가능성을 검토해야 한다. 이번에 실증된 결함으로 분류하지 않았다.

포지션 미등록 회원은 수동으로 기본 포지션에 배정할 수 있지만 일반 ‘교대’ 추가 자리에서는 저장 변환에 주포지션이 필요하다. 따라서 ‘수동 배정하면 어디든 해결’이라고 안내하면 안 된다. 이는 자동 배치 사유와 별개의 수동 저장 경계다.

자동 배치 이후 수동 해제·교체·팀/줄 삭제 또는 신청자 변경으로 생긴 미배정을 이전 자동 배치의 실패로 설명해서도 안 된다. 결과 리포트는 편집 시 무효화하거나 현재 명단으로 다시 계산해야 한다.

## 재현된 결함 — 팀 삭제 후 자동 배치 무반응

1. A/B/C팀과 등록된 신청자 2명을 준비한다.
2. A팀에 한 명을 수동 배정한다.
3. D팀을 추가하고 D팀을 삭제한다.
4. 자동 배치 확인창에서 실행한다.
5. 기대: 남은 한 명도 배정되어 2명. 실제: 1명 그대로.

`confirmTeamDeletion`은 삭제하지 않은 팀의 `target`은 보존하면서 `pendingId`만 null로 바꾼다. 해당 target이 기존 선수의 자리이면 `isPending`이 true가 되어 reducer의 auto 분기가 아무 변경 없이 반환된다. 자리도 프로필도 충분한데 사용자가 실패 원인을 알 수 없다.

수정 시 삭제 후 target/pending 상태를 일관되게 정리하고, 실제 명령이 실행되지 않은 경우 정상 결과 안내를 만들지 않아야 한다. 최신 모달형 배정에서는 과거 보류 선택 guard의 유효성도 함께 점검한다. 이번에는 수정하지 않았다.

## 사유 안내 설계 기준

- 자동 배치 후 활성 신청자가 남았을 때만 기존 상태 줄에 `신청자 4명 남음 · 이유 보기`를 제공한다. 상시 박스를 추가하지 않는다.
- 기본 그룹: `주포지션 미등록 N명`, `빈자리 부족 N명`. 이름·소속과 현재 가능한 해결 행동을 함께 표시한다.
- 한 사람은 대표 사유 한 곳에만 집계하여 그룹 합계가 잔여 신청자 수와 일치하게 한다.
- 포지션 불일치는 잔여 사유로 쓰지 않는다. 필요한 경우 이미 배정된 결과의 ‘주·부 이외 포지션 배정’ 정보로 별도 취급한다.
- 실행 실패는 `자동 배치를 완료하지 못했습니다` 등 별도 오류로 처리한다. 이번 발견된 상태 결함을 선수 사유로 포장하지 않는다.
- 모든 신청자가 배정되었다는 안내와 공개 가능 여부는 기존 공개 검증 결과를 각각 따른다.

## 검증 증거와 재실행

합성 조건 12개와 결정적 생성 입력 2,000개를 실제 `autoFillBoard`에 실행했다. 2,000개 검사에서 활성·주포지션 등록 신청자가 남으면서 유효한 빈자리가 있는 반례는 없었다. 이 검사는 함수 정상 실행 결과에 대한 것이며 UI 명령이 실행되지 않는 오류를 보장하지 않는다.

- `unassigned-probe.mjs` / `unassigned-probe-results.json`: 합성 입력과 결과. worktree의 web 디렉터리에서 `node ../docs/reviews/auto-allocation-feedback-20261008/unassigned-probe.mjs` 실행.
- `team-delete-autofill.test.tsx.txt`: 실제 컴포넌트 회귀 재현. 검증 당시 임시로 web/tests에 넣어 실행했고 원상 제거했다. 수정 시 정식 회귀 테스트로 이동하여 사용할 수 있다.
- `team-delete-autofill-result.txt`: 해당 테스트 1건 실패, 기대 2명/실제 1명. 결함 발견 증거이며 통과로 보고하지 않는다.
- 10월17일 실제 입력은 앞선 읽기 전용 분석에서 18명 중 미등록 4명, 등록된 14명 배정으로 확인했다. 이번 합성 검증은 실제 명단/저장본을 변경하지 않았다.

주요 코드: `web/components/sideout/allocation/allocation-ab-model.ts:59` 자동 배치, `:31` isPending, `:117` 실행 차단; `session-allocation.tsx:24` 수동 용량, `:66` 팀 삭제, `:90` 잔여 수, `:114` 자동 배치 진입; `web/lib/sideout/allocation-adapter.ts:19` 미등록 일반 추가 자리 저장 제한.

후속 순서: ① 재현된 팀 삭제/자동 배치 결함 수정 및 회귀 테스트 ② 기존 알고리즘을 유지한 결과·사유 계산 ③ 복합 사유/대기자 점유/수동 변경 무효화 검증 ④ 모바일 이유 보기 UI와 미등록 일반 추가 자리 해결 경로 검토.
