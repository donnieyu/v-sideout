# 포지션 입력 인수 및 통합 준비

## 확인된 포지션 인수 상태

- 인증 원본: `.worktrees/auth-rotation`, `feat/auth-rotation`, HEAD `3c2c018`, 조사 시 작업 트리 clean.
- 인수 문서: `docs/reviews/MEMBER_POSITION_PROFILE_P3_HANDOFF_2026-10-03.md`.
- 명시 인수는 권한 있는 팀편성 후보의 **조회 및 최소 테이블** 범위다. 개인 주·부 `S/MB/OH/OP`, 동일 주·부 허용. 미등록은 null이고 배정값에서 추론하지 않는다.
- 실제 승인 저장 경로: `web/lib/auth/join-approval-repository.ts`. 기존 사전등록/직접추가 회원에게 프로필을 편집하는 UI/API는 양 작업 트리에 없다. 다른 담당자의 작업이 완료됐다고 표시하지 않는다.
- 후속 구현 전 정해야 할 계약: 본인 수정/운영진 대리 수정 권한, 회원 관리와 내정보 중 진입 위치, 프로필 revision 및 동시 수정, 승인 시 최초값과 직접 수정값 우선순위. 기존 조회 인계를 쓰기 소유권 인계로 해석하지 않는다.
- 이번 단계는 인수 상태 확인 완료이며, 포지션 입력 구현 완료가 아니다. 실제 구현은 별도 계약·담당 인수 이후 진행한다.

## 통합 경계와 제안 순서

1. promotion-p1의 현행 UI/참가/편성/경기 변경을 기능 묶음별로 확정하고 해당 검사·증거를 함께 검토한다. 기존 대량 미커밋 변경을 이번 ID 보완만의 변경으로 묶지 않는다.
2. 인증 담당은 auth-rotation의 고정 커밋과 가입/승인/발송/제한기 계약을 인계하고, 통합 담당은 승인된 소유권 범위에서 합류한다.
3. DB migration 계보를 단일화한다. promotion의 `0003_milky_night_thrasher.sql`과 auth의 `0003_chubby_sugar_man.sql`은 서로 다른 변경이며 auth `0004_wet_liz_osborn.sql`도 프로필 테이블을 생성한다. 번호뿐 아니라 Drizzle journal/snapshot 및 이미 적용된 테이블을 대조해야 한다. 양쪽을 그대로 연달아 실행하면 중복 테이블 위험이 있다.
4. 새 합성 DB와 기존 로컬 DB의 복사본에서 각각 초기 설치/업그레이드를 검증한다. 실제 회원 DB나 원격 D1에 미검증 migration을 적용하지 않는다.
5. 통합된 브랜치에서 인증·회원·참가·팀·경기 전체 회귀, 다중 계정 접근, 저장 실패·재시도·권한회수·응답 유실을 검증한다.
6. iPhone 잔여 검수와 출시 범위를 확정한다. 모임 공간/게시판은 기존 기능 보존 및 새 셸 진입 인수가 남아 있다.
7. 배포 대상/환경변수/도메인을 확정한 뒤 별도 배포. 합성 계정·연습 일정은 실서비스 회원 데이터로 이전하지 않는다.

## 배포 및 복구 준비 체크

- 배포 전: 현재 DB 백업을 생성하고 복원 시험, 적용 migration 목록·스키마·코드 커밋을 함께 기록.
- staging: 합성 데이터로 회원별 접근·신청/취소·공개/취소·경기 수정 smoke, 오류 응답과 세션 만료 확인.
- release: 불변 코드 산출물/환경 설정/DB 버전을 한 묶음으로 고정. 인증 발송 채널의 실제 설정은 인증 담당 계약을 따른다.
- 실패 시: 서버 쓰기를 제어하고 우선 호환되는 이전 코드로 복귀. DB 파괴적 다운 migration을 자동 실행하지 않는다. 데이터 복원은 이후 정상 쓰기 손실을 평가한 후 실행한다.
- 완료 증거: 공개 URL/권한별 smoke/로그 확인/복원 기록. 현재 4180 로컬 URL은 이 증거를 대체하지 않는다.

이번 작업에서는 커밋·병합·원격 DB 변경·운영 배포를 실행하지 않았다.
