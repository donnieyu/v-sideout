# SIDEOUT 모바일 연속 배정 — 높이와 비교 경험 검토

2026-09-24 · B 발전 방향 제안 · 로컬 샘플 실측 · 운영 앱 미적용

**후속 결정·구현:** 사용자는 요약 배치판과 선수 풀 스크롤을 선택하고 포지션별 배정을 기본으로 확정했다. 자율 배치 화면 선택지는 보류했다. 현재 B 체험본의 동작과 검증은 [v4 포지션별 배정](MOBILE_POSITION_FLOW_V4.md)을 따른다. 아래 세 방식 비교는 선택 전 분석 기록이다.

## 결론

**현재 선택에 필요한 배치 요약과 선수 풀의 동시 확인을 기본으로 하고, 전체 구성은 필요할 때 펼쳐 확인하는 방식**을 추천한다. 배치판 전체를 항상 고정하는 것도, 매번 위아래를 왕복하게 하는 것도 기본 경험으로 삼지 않는다.

순환 배정에서는 선수를 고른 직후 대상 자리가 바뀐다. 현재 대상이 보이지 않으면 사용자는 ‘방금 누구를 어디에 넣었는지’와 ‘다음 배정 위치’를 기억해야 한다. 따라서 후보를 보고 있는 동안에도 현재 자리와 직전 결과는 유지해야 한다. 반면 24~28명의 모든 정보와 충분히 큰 후보 버튼을 작은 화면에 동시에 노출하는 것은 현실적인 목표가 아니다.

- [높이·단계별 구조 비교 도식](http://localhost:4173/weekend/mobile-height-review/)
- [탭을 정리한 현재 B 체험본](http://localhost:4173/weekend/allocation-ab/)
- [보존된 A 참고본](http://localhost:4173/weekend/allocation-reference-a/?variant=a)

비교 도식은 화면 높이 선택, 포지션별/자율 단계 선택, 목록 스크롤만 작동한다. 배정·해제·저장 기능을 옮긴 신규 목업이 아니다. 이번에 실제 B에 적용한 변경은 A/B 전환 탭 정리와 B 기본 진입뿐이다.

## 1. 확인한 현재 상태

인앱 브라우저의 CSS 뷰포트를 390×844, 360×740, 320×568로 변경하고 가상 선수를 배정하면서 확인했다. 아래 높이는 반올림한 값이며 브라우저 주소창, 키보드, 실기기 안전 영역을 포함하지 않는다.

390×844에서 하단 내비게이션은 67px, 이를 제외한 공간은 777px였다.

| 현재 배정 단계 | 고정 배치판 높이 | 777px 중 비율 | 영향 |
|---|---:|---:|---|
| 세터 | 241px | 31% | 한 자리씩인데도 팀 제목·안내·타일 높이가 누적됨 |
| 레프트·센터 | 352px | 45% | 팀별 두 자리 세로 배열로 후보 공간이 감소 |
| 자율 배치 | 480px | 62% | 팀별 다섯 자리 세로 배열이 대부분을 차지 |

확인한 중요한 차이:

1. **첫 진입 후보 노출 부족:** 기존 A/B 탭 포함 화면에서는 첫 후보 시작점이 약860px였다. 탭 제거 후 약782px로 78px 개선되었으나, 하단 바 시작점777px보다 아래이므로 온전히 보이는 후보는 여전히 0개다.
2. **긴 화면에서 동시 비교는 일부 가능:** 844px 화면에서 스크롤 후 레프트 배치판과 후보 4개, 자율 배치판과 후보 3개를 함께 볼 수 있었다. 현재 구현 전체가 쓸 수 없는 것은 아니다.
3. **짧은 화면에서는 경험이 달라짐:** 자율 배치는 화면 높이740px 이하에서 고정이 해제된다. 360×740에서 후보 목록까지 더 내려가면 후보8개가 보이는 대신 배치판은 화면 밖으로 사라졌다. 568px에서는 모든 배치판의 고정이 해제된다.
4. **앞선 단계 정보가 유지되지 않음:** 앞선 포지션 요약은 별도 문서 흐름에 있어 스크롤 밖으로 사라진다. 현재 포지션 고정만으로는 ‘앞서 배정한 선수와 비교’ 요구를 모두 충족하지 못한다.
5. **검색도 배치판 뒤로 이동:** 후보 목록까지 내려간 상태에서 검색·범위 선택이 고정 배치판 뒤로 가려진다. 비교 대상뿐 아니라 후보를 다시 좁히는 조작도 왕복을 요구한다.

## 2. 구성 방법 비교

| 방법 | 이점 | 비용·한계 | 적합한 용도 |
|---|---|---|---|
| 화면 전체 스크롤 | 후보를 넓게 읽고 목록 탐색 가능, 구조 단순 | 현재 대상과 앞선 배정을 기억하며 왕복해야 함 | 완성 결과 검토, 아주 짧은 화면의 보조 방식 |
| 전체 배치판 고정 | 현재 포지션의 모든 자리를 계속 비교 | 자율 배치·4팀·큰 글자에서 후보가 거의 남지 않음 | 화면 높이가 충분한 환경 |
| **요약 배치판 고정** | 대상·최근 결과·팀 비교를 유지하며 후보 공간 확보 | 무엇을 요약하고 펼칠지 규칙이 필요 | **모바일 최초 전체 편성의 기본 방식** |
| 배치/후보를 별도 탭으로 전환 | 각 화면의 공간을 충분히 확보 | 반복 전환과 기억 부담, 연속 배정 장점 약화 | 기본 방식으로 비추천 |
| 높이를 손으로 조절하는 분할 패널 | 사용자가 비교/후보 공간을 선택 | 조작법 학습, 터치 충돌, 접근성 구현 부담 | 후속 실험으로 보류 |

높이740px 비교 도식에서 전체 자율 배치판 고정은 후보 영역이 약61px, 요약 방식은 약251px 남았다. 이것은 도식의 수치이며 실제 B의 개선 결과가 아니다. 높이568px에서는 요약 방식도 약79px만 남으므로, 단순 축소만으로 충분하지 않다는 것도 확인했다.

## 3. 권장 화면 구성

### 공통 원칙

- 상단 제목·진행 정보·모드·포지션 탭을 모두 큰 블록으로 쌓지 않는다. 제목/총배정 수, 현재 단계, 배치 요약으로 압축한다. 모드·자동 배치 기능은 접근 가능하게 유지하되 후보 선택 중 항상 큰 높이를 차지하지 않도록 한다.
- 후보 목록을 주 스크롤 영역으로 둔다. 배치 요약과 검색은 후보 스크롤로 없어지지 않게 한다. 모바일 전체 페이지와 후보 영역이 동시에 스크롤되는 상황은 최소화한다.
- 하단 `이전 · 전체 팀 · 다음`의 위치는 고정한다. 전체 팀에서 `배정으로` 복귀하면 단계·대상·검색·후보 스크롤 위치를 유지한다.
- 배정 직후 위로 자동 스크롤하지 않는다. 요약의 이름과 현재 대상만 갱신하고 직전 배정 결과를 짧게 표시한다. 다음 포지션 자동 전환은 하지 않는다.
- 후보가 목록에서 빠지면서 다음 버튼이 손가락 아래로 급격히 이동해 연속 오터치가 나지 않는지도 확인한다. 두 번 탭·연속 터치 검증이 필요하다.

### 포지션별 배정

기존의 ‘A/B/C 세로 열 + 높이가 큰 자리 타일’ 대신 **팀별 한 행, 현재 포지션 자리별 열**의 작은 비교표를 제안한다. 레프트라면 `A | 레프트1 | 레프트2`, `B | …`, `C | …`로 읽는다.

- 팀 이름 옆 또는 아래에 앞서 지정한 세터 이름을 계속 표시한다.
- 현재 포지션의 배정된 이름과 빈자리는 항상 비교한다. 현재 대상은 색과 외곽선·텍스트로 구분한다.
- 센터 이후의 앞선 모든 포지션 이름까지 상시 펼치면 다시 높아진다. 세터는 기본 유지, 나머지는 ‘앞선 배정 펼치기’나 전체 팀에서 확인한다. 전체 이름을 항상 노출한다는 이전 구상을 현실적인 요약 정책으로 구체화하는 제안이다.
- 현재 자리 선택과 X 해제는 서로 충분한 터치 공간을 갖게 한다. 이름·X·선택 동작을 작은 한 셀에 무리하게 넣지 않는다. 선택된 셀에서 해제를 제공하는 방식도 비교 후 결정한다. 기존 X 확인 절차는 유지한다.

### 자율 배치

15개의 일반 자리 타일을 항상 펼치지 않는다. **A/B/C 팀별 이름 요약 + 현재 대상 자리**를 보여준다. 이름 요약에서 세터를 구분하되 코트 위치를 확정한 것으로 표현하지 않는다.

배정 인원이 많아지면 모든 이름을 줄바꿈하는 대신 팀별 요약의 높이를 제한하고 나머지는 명시적으로 펼쳐 확인한다. 현재 대상 팀은 조금 더 자세히, 다른 팀은 비교 가능한 핵심 이름과 인원수를 유지하는 방안이다. 4팀일 때 어느 팀을 숨길지 자동 결정하는 방식보다 모든 팀의 요약 행을 유지하는 쪽이 낫다.

### 화면이 짧거나 키보드가 열린 경우

배치판을 통째로 없애지 않고 **현재 대상 + 직전 배정**으로 축약한다. `배치 보기`를 통해 다시 펼칠 수 있게 한다. 키보드가 닫히면 직전 표시 상태로 복원한다. 상단 전체 비교가 잠시 줄어드는 것은 허용하되, 대상 자리까지 사라지는 것은 피한다.

‘740px 이하이면 고정 해제’ 같은 단일 기준보다 실제 남는 후보 영역을 기준으로 축약해야 한다. 목표는 일반 높이에서 후보 카드2~3개 이상을 읽는 것이며, 글자 확대·키보드 상황에서는 후보 최소1개와 배정 대상 접근을 우선한다. 숫자는 개발 목표이지 아직 검증된 보장이 아니다.

## 4. 헬퍼·LLM으로 연결하는 관점

현재 수동 작업에서 필요한 입력은 배정 대상, 현재 구성, 후보, 조건이다. 이 구조를 유지하면 향후 헬퍼가 후보/조건 영역에서 제안하고 운영자가 적용하는 방식으로 연결할 수 있다. 대화 전체를 상단에 쌓으면 같은 높이 문제가 재발하므로, 최신 질문과 선택지를 보여주고 이전 대화는 별도 펼침으로 두는 편이 적합하다.

지금 LLM 연동이나 대화 UI를 먼저 만들 필요는 없다. 먼저 요약된 배치판으로 수동 연속 배정이 편리한지 검증하고, 동일한 배정 상태·검증 로직 위에 헬퍼를 연결한다.

## 5. 이번 반영 및 다음 검증

### 반영 완료

- 활성 체험 화면에서 A/B 전환 탭 제거, 기본 진입을 B로 변경.
- A의 빌드와 소스 스냅샷을 `allocation-reference-a/`에 별도 보존.
- 기존 B의 순환 배정·모드 전환·후보 규칙은 변경하지 않음.
- 기존 모델 검사67개, UI 통합 검사2개, TypeScript와 Vite 빌드 통과.
- 변경 마크업 Impeccable detector 결과 항목 없음.

### 아직 제안인 것

요약 비교표, 앞선 배정 펼침, 키보드 대응, 후보 영역 별도 스크롤은 실제 B에 적용하지 않았다. 구조 비교 도식으로 장단점과 공간 한계를 먼저 확인할 수 있다.

### 선택 후 진행 순서

1. **완료:** 포지션별 세터→레프트 흐름에 요약 비교표와 선수 풀 스크롤을 적용했다. 자율 배치는 후속 검토로 미뤘다.
2. 3팀의 첫 편성을 끝까지 해보며 현재 대상 식별, 이전 선수 비교, 후보 검색, X 해제, 전체 팀 왕복을 함께 평가한다.
3. 높이568/740/844, 4팀·7명, 긴 이름, 글자 확대, 키보드에서 축약 정책을 검증한다. 실제 iOS/Android 터치 검증은 별도로 수행한다.
4. 검토한 구조를 확정한 뒤 저장·공개와 일정 상세에 통합하고, 이후 규칙 기반 헬퍼를 발전시킨다.

실제 로그인·계정 발급·DB·운영 앱 반영은 이번 범위가 아니다. 모든 배정 검사는 가상 데이터로 진행했다.
