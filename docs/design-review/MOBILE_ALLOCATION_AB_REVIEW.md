# 모바일 최초 팀편성 — A/B 비교와 헬퍼 전환 검토

2026-09-23 · 기획 비교안 · 실행 화면 미변경

## 1. 최신 사용자 결정

- A/B 비교로 진행한다.
- 우선 과제는 **처음 전체 팀을 편성하는 과정**이다. 완성 후 선수 한두 명을 수정하는 별도 과정을 기획한다.
- 주 사용 환경은 PC가 아니라 **모바일**이다.
- 최종 목표는 대화와 선택을 이어가며 헬퍼가 편성을 돕고, 이후 운영자가 수동 조정하는 경험이다. 추후 LLM을 연결한다.
- 지금 당장 자동 편성/LLM을 구현하라는 뜻은 아니다. 수동 기능과 헬퍼의 개발 순서를 비판적으로 검토한다.

이 결정은 이전 보고서의 ‘넓은 화면 후보 패널 우선’ 추천보다 우선한다. 이미 확정한 Dialog 적용, 최초 초안 저장, 수정→저장, 별도 공개, 배정 버튼만 사용/X해제는 유지한다. 이번 문서는 구조 비교이며 실제 UI를 바꾸거나 새로운 규칙을 확정하지 않는다.

## 2. 핵심 평가

**모바일·최초 전체 편성이 우선이면, 완성된 코트에서 한 자리씩 수정하는 방식만 개선해서는 부족하다.** 초기에 보게 되는 것은 빈칸18~24개이고 해야 하는 일은 세터와 가용 선수를 여러 팀에 분배하는 것이다. 공개 결과를 읽기 좋은 코트와 최초 편성을 빠르게 만드는 작업 화면은 목적이 다르다.

‘수동을 먼저 만든다’는 방향은 타당하다. 헬퍼가 잘못 배정했을 때 사람이 수정할 수 있어야 하고, 헬퍼도 동일한 배정·중복 검사·초안 저장을 사용해야 한다. 다만 **수동 화면을 완전히 마감한 뒤 헬퍼 경험을 처음 설계하는 순서**는 재작업 위험이 높다. 자리별 검색에 최적화된 구조와 대화/조건/일괄 초안의 구조가 달라질 수 있기 때문이다.

추천 순서는 **헬퍼의 전체 경험을 먼저 얕게 설계 → 공통 편성 모델과 모바일 수동 최초 편성 개발 → 수동 미세 조정 기획 → 규칙 기반 헬퍼 → LLM 연결**이다. 수동 미세 조정의 상세 기획은 사용자 요청대로 최초 전체 편성 평가 이후 진행한다. 단, 최초 편성 중 실수를 되돌리는 적용 취소·X해제는 지금도 필요하다.

## 3. 이전 제안에서 바꿔야 할 판단

| 이전 접근 | 모바일 우선일 때의 문제 | 수정된 방향 |
|---|---|---|
| 모든 코트를 크게 보이고 후보 패널을 옆에 둠 | 폭 부족. 둘 다 작아지거나 후보 선택 시 팀들이 사라짐 | 같은 역할의 팀별 요약을 위에 유지하고 후보를 아래에 둠 |
| 결과용 코트가 기본 편집 공간 | 반복 스크롤과 빈자리 탐색이 많음 | 코트/행은 전체 검토에 유지, 연속 배정 작업 공간을 비교 |
| 한 자리 변경을 여러 번 반복하면 전체 편성 |18~28명 최초 배정의 반복 비용을 놓침 | 처음부터 다수 배정 과제로 A/B 평가 |
| 수동 기능을 모두 완성한 뒤 헬퍼 검토 | 헬퍼 요구가 상태/데이터 구조를 다시 바꿀 수 있음 | 경험·명령 경계는 먼저 설계, 자동 생성과 LLM 구현은 뒤로 |
| 자연스러운 대화 = 자유 입력 채팅 | 모바일 입력·대화 재독·조건 기억 부담 | 선택 카드 우선, 자연어는 예외 조건·조정 의도에 사용 |

## 4. A/B의 공통 조건

비교에서 디자인 장식·샘플 선수·정책을 다르게 하지 않는다. 두 안 모두 C+B 색/밀도, 같은 shadcn 컴포넌트, 이름·소속·프로필 정보 범위를 사용한다. 코트 전위 오른쪽 세터, 레프트2·센터2·라이트1·세터1, 복수 교대 줄, 미배정 우선, 우선 보장, 공개 분리는 공통이다.

초기 입력은 같은18명·빈3팀·모든 선수 미배정으로 맞춘다. 첫 시나리오는 충분한 주 포지션 인원이 있는 경우, 이후21/24/28명과 부족/중복 역할 사례를 추가한다. 인원이18·21·24·28이어야만 편성할 수 있도록 제한하지 않는다. 이 수는 검토용 대표 사례다.

최초 진입은 `신청 인원 확인 → 팀 수/구성 확인 → 수동 배정 → 전체 검토 → 초안 저장`으로 공통화한다. 첫 비교에서 자동 추천·드래그·LLM을 한 안에만 넣지 않는다. 데이터는 검토용이며 실제 실력·접수 기록으로 오해하지 않게 한다.

## 5. A안 — 자리 중심의 모바일 보드

기존 방식의 개선안이다. 모든 팀을 세로로 이어서 표시하고 빈 자리에서 선택창을 연다. 특정 팀 탭만 남겨 다른 팀을 숨기지 않는다.

```text
뉴배동 · 운동 날짜
팀편성                 [초안 저장]
배정 0/18    미배정 신청 18
[코트] [행]

A팀 0명
레프트   센터   세터 +
레프트   센터   라이트
[+ 교대 자리]

B팀 0명 …
C팀 0명 …
```

```text
A팀 · 세터에 배정
현재 배정 / 변경 예정 (있을 때)
[검색] [역할 범위] [미배정만]

김도윤 · 주 세터       [배정]
서유진 · 주 세터       [배정]
이도현 · 주 세터       [배정]

변경 영향
                   [닫기] [적용]
```

흐름: A세터 자리 → 후보 배정 → 적용 → 보드 복귀 → B세터 자리 → 반복. 언제든 다른 역할부터 채울 수 있다. 닫기는 해당 Dialog 변경만 폐기한다.

장점:

- 어디에 넣는지 명확하고 지금까지 검토한 상호작용을 많이 활용한다.
- 코트와 실제 편집 결과가 같은 자리 구조여서 배우기 쉽다.
- 후보 선택에 화면을 충분히 쓸 수 있다.

약점:

- 모든 팀의 세터를 먼저 분배하려면 팀 사이 스크롤과 선택창 재진입이 반복된다.
- 후보를 고를 때 다른 팀의 세터/인원 구성은 기억해야 한다. 변화 요약이 보완하지만 전체 비교를 대체하지는 못한다.
- 회원 결과를 위한 큰 코트가 편집 때는 높이를 차지한다.

이 안은 비교 기준선이다. 아직 만들어지지 않은 자동 다음 자리 이동을 기본 장점으로 계산하지 않는다.

## 6. B안 — 팀별 요약 + 연속 수동 배정

이전 B의 ‘팀과 후보를 동시에 본다’는 목적은 유지하되 옆 패널을 없앤다. 화면을 **상단 비교 요약 / 하단 후보 작업**으로 나눈다. 자동 생성 없이 운영자가 한 명씩 결정하므로 아직 헬퍼는 아니다.

```text
뉴배동 · 운동 날짜
수동 팀편성              [전체 팀]
배정 0/18        미배정 신청 18
[세터] [레프트] [센터] [라이트] [교대]

         A팀      B팀      C팀
세터     +        +        +
         ↑ 현재 편집 대상
──────────────────────────
A팀 · 세터에 배정
현재 배정 / 변경 예정 (있을 때)
[검색] [역할 범위] [미배정만]

김도윤 · 주 세터        [배정]
서유진 · 주 세터        [배정]
이도현 · 주 세터        [배정]

변경 영향
                [되돌리기] [적용]
```

흐름: 상단 A팀 세터 선택 → 아래 후보 배정 → 적용 → 상단 B팀 세터 선택 → 같은 후보 영역에서 반복. 적용하면 그 선수는 미배정에서 빠지고 팀별 요약이 갱신된다. 검색 범위와 스크롤은 불필요하게 초기화하지 않는다. 원치 않는 검색어를 쉽게 지울 수 있어야 한다.

세터는 시작 초점일 뿐 필수 순서가 아니다. 역할 탭은 작업 대상 필터다. 이전에 없애기로 한 팀 명단 내부의 큰 포지션 그룹과 포지션별 집계를 되살리지 않는다. 레프트/센터는 팀별 두 자리, 세터/라이트는 한 자리로 표시한다.4팀에서는 이름을 과도하게 줄이지 않도록 요약을2×2로 배치하는 안을 검증한다.3열을 모든 폭에 강요하지 않는다.

`전체 팀`에서 같은 데이터의 코트/행을 확인하고 다시 작업으로 돌아온다. 상세 전체를 작은 화면 하나에 모두 넣으려 하지 않는다. 후보 목록이 길어져도 현재 대상 팀·역할은 놓치지 않게 유지한다.

장점:

- 여러 팀의 같은 역할을 한 화면에서 비교하면서 연속 배정한다.
- 후보 목록을 반복해서 열 필요가 없고, 세터 분산 후 다른 역할로 이어가기 쉽다.
- 미래 헬퍼도 같은 팀 요약·후보·변경 미리보기를 사용할 수 있다.

약점과 설계 과제:

- 현재 편집 대상이 불분명하면 A팀에 넣으려던 선수를 B팀에 넣는 오류가 생길 수 있다. 대상 강조와 `A팀 · 세터에 배정`을 유지해야 한다.
- 미적용 변경이 있을 때 다른 팀/역할을 누르는 동작을 정해야 한다. **제안:** 새 곳으로 조용히 이동하지 않고 하단 적용/되돌리기를 사용하게 한다. 새 확인창을 매번 띄우는 방식은 피한다.
- 대기자가 많거나 키보드가 올라오면 상단 요약·검색·행동이 후보 공간을 잠식할 수 있다. 고정 영역을 실제 기기에서 검증해야 한다.
- 적용 직후 다음 빈자리로 자동 이동하는 것은 별도 제안이다. 첫 비교에서는 직접 다음 자리를 선택하게 해 방향 혼란을 줄인다.

하단 `되돌리기`는 B의 비모달 영역을 위한 제안이다. Dialog의 확정된 `닫기/적용` 명칭을 임의로 바꾼 것이 아니다. 이미 적용된 전체 편집을 되돌리는 기능과도 구분한다. 실제 B 구현 전 이 상태 전이를 명세에 추가한다.

## 7. 비교 판단

| 기준 | A 자리→선택창 | B 팀 요약+연속 배정 |
|---|---|---|
| 첫 사용 이해 | 유리: 빈자리에 넣기 | 대상 팀과 역할 선택을 학습해야 함 |
| 세터3~4명 분산 | 팀 간 이동 반복 | 같은 화면의 팀 요약에서 비교 |
|18~28명 최초 배정 | 매번 선택창 진입/복귀 | 작업 맥락 유지 가능 |
| 모바일 세로 공간 | 코트+반복 스크롤 | 요약과 후보의 높이 관리 필요 |
| 전체 팀 결과 확인 | 보드에서 바로 확인 | 전체 팀 보기로 전환 필요 |
| 단순 수동 수정 | 친숙한 기반, 상세 기획은 후속 | 최초 편성 최적화, 수정 흐름은 별도 검토 |
| 헬퍼와 연결 | 결과 수정 화면으로 재사용 | 단계 안내·후보·초안 검토 구성으로 재사용 |
| 실패 위험 | 맥락을 기억해야 함 | 활성 대상 혼동·미적용 변경 처리 |

**현재 가설은 최초 전체 편성에서 B가 유리하고, A는 직관성의 기준선이라는 것이다.** 아직 클릭 수/소요시간/실수율을 측정하지 않았으므로 B를 확정하지 않는다. B가 더 좋더라도 전체 결과 확인과 후속 미세 수정에서 A의 장점은 재사용할 수 있다.

## 8. 수동과 헬퍼 개발 순서에 대한 비판적 평가

| 순서 | 장점 | 위험 | 평가 |
|---|---|---|---|
| 수동 UI 완성 → 헬퍼 기획 | 당장 쓸 수 있는 편집기에 집중 | 헬퍼용 조건/초안/대안 상태를 뒤늦게 설계, 버릴 UI를 과도하게 다듬음 | 그대로 따르기보다 범위를 줄여야 함 |
| LLM 헬퍼 먼저 → 수동 보완 | 최종 경험을 빨리 흉내 냄 | 잘못된 배정·부족 정보·권한 문제를 대화로 가림, 수정 기반 없음 | 현재에는 권하지 않음 |
| 헬퍼 경험 선설계 → 수동 공통 기능 → 규칙 헬퍼 → LLM | 최종 목적과 개발 기반이 연결됨 | 초기에는 화면보다 상태/명령 설계가 필요 | 추천 |

‘수동 기능 완성’의 종료 조건을 정한다. 최초 편성, 적용/취소, 중복 방지, 교대, 보장 검토, 초안 저장/공개 분리를 신뢰할 수 있으면 다음 단계로 갈 수 있다. 수동 작업의 모든 편의 기능·고급 드래그·맞교환·단축키를 먼저 만들 필요는 없다.

사용자 요청대로 **경기 직전 한두 명 수정의 전용 UX는 최초 편성 A/B 평가 뒤**에 기획한다. 최초 편성 중의 실수 복구는 후순위로 미루지 않는다. 이는 별도 수정 워크플로를 선행 개발하자는 뜻이 아니다.

## 9. 최종 헬퍼 경험 — 채팅만으로 만들지 않는다

최종 흐름 제안:

```text
신청/대기/보장 인원 확인
 → 몇 팀인지 선택
 → 필요한 추가 조건만 질문
 → 세터 및 역할 가용성 확인
 → 초안 생성
 → 팀 요약·문제·대안 표시
 → 운영자 선택 또는 자연어 조정
 → 수동으로 필요한 자리 조정
 → 초안 저장 / 이후 공개
```

선택형 질문으로 답할 수 있는 조건은 버튼/카드로 제공한다. 회원 정보나 이미 선택한 조건을 대화에서 반복 입력하게 하지 않는다. 모든 포지션 후보를 한 명씩 질문하면 수동보다 느려질 수 있으므로, 기존 가용 정보와 차이가 있을 때만 묻는다.

대화 내용과 별도로 `현재 조건`과 `현재 편성안`을 화면에서 확인할 수 있게 한다. 대화 스크롤을 읽어야 팀 수나 고정 선수를 기억할 수 있는 구조는 피한다. 자연어는 ‘세터는 유지하고 센터만 다시 나눠줘’ 같은 변경 의도를 입력하는 데 활용한다. 이 기능은 후속 예시이며 현재 확정·구현된 명령이 아니다.

헬퍼가 계속 질문만 하는 것도 실패다. 데이터가 충분하면 제안을 내고, 부족하거나 모순된 조건만 질문해야 한다. 세터가 팀 수보다 적거나 보장 인원이 수용 범위를 넘으면 모르는 사람을 채우거나 조용히 제외하지 않는다.

LLM과 코드의 책임을 분리한다.

| 역할 | 맡길 일 | 맡기지 않을 일 |
|---|---|---|
| 화면 | 조건 선택, 후보/편성/변경 영향 확인, 수동 수정 | 대화 이력만을 상태의 유일한 근거로 사용 |
| 코드 | 참가자 ID·권한·가용 역할·중복·보장 검증, 초안 생성/저장/공개 | 프로필 데이터 없이 실력 추정 |
| LLM (후속) | 자연어 의도 해석, 필요한 질문, 검증된 결과 설명, 대안 요청 | 임의 회원 생성, 누락 은폐, 권한/보장 우회, 자동 공개 |

자연어 요청도 구조화된 변경안으로 변환하고 같은 검증을 통과해야 한다. LLM이 없거나 응답하지 않아도 선택 카드·규칙 헬퍼·수동 수정은 동작해야 한다. 인공지능 도입 자체를 완료 기준으로 삼지 않는다.

실력 월드컵은 별도 평가 기능이다. 헬퍼 첫 버전의 선행 조건으로 묶지 않는다. 먼저 운영자가 입력한 평가/미평가를 구분하고, 투표 방식의 반복 비교·편향·공개 범위를 후속 검토한다. 투표를 통한 점수를 객관적 실력으로 단정하지 않는다.

## 10. 공통 기능을 먼저 설계할 이유

수동 A/B, 규칙 헬퍼, LLM은 동일한 편성 작업에 대한 다른 입력 방법이다. 구현 제안은 다음과 같다.

```text
수동 입력 ─┐
규칙 초안 ─┼→ 변경안 → 검증 → 편집본 → 초안 저장 → 공개본
자연어 해석┘             ↑
                      사람의 확인
```

변경안에는 대상 회차·참가자 ID·대상 자리·기준 버전·누가 빠지는지·어떤 자리가 비는지가 포함되어야 한다. 자연어 문장을 직접 DB 수정으로 연결하지 않는다. 전체 새 초안과 일부 자리 수정도 원본을 덮어쓰기 전에 비교할 수 있어야 한다.

모바일에서는 중단 후 복귀도 중요하다. 편집 도중 앱 전환/잠금/새로고침을 구분하고 복구 정책을 설계해야 한다. **제안:** 복구용 임시 상태는 명시적인 초안 저장/공개와 구분한다. 이는 현재 미구현이며 자동 저장으로 공개 범위를 바꾸자는 뜻이 아니다.

## 11. A/B 평가 계획

처음에는 동일 인원으로 짧은 흐름을 확인하고, 구조 선택 후 전체18~28명 과제를 수행한다. 예쁜 정지 화면만 보고 승자를 정하지 않는다.

| 차수 | 공통 과제 | 확인할 것 |
|---|---|---|
| 1 구조 비교 | 빈3팀의 세터3명 수동 배정, 센터2명 추가, 전체 확인 | 대상 팀 이해·비교 맥락·스크롤·복귀 |
| 2 최초 편성 | 동일18명 전체 배정→검토→초안 저장 | 왕복 횟수·소요시간·오배정·누락·취소 |
| 3 범위 확장 |21/24/28명,4팀,복수 교대,여러 역할 가능 선수 | 데이터/레이아웃 일관성,후반부 역할 부족 |
| 4 예외 |세터 부족,보장 누락,신입/임시 인원,중간 중단 | 문제 발견·복구·정책 이해 |

360~430px 폭을 우선 평가하고320px 및 큰 글꼴을 경계 조건으로 확인한다. 실제 키보드·한 손 조작·앱 전환은 기기에서 검증해야 한다. 주 기기(OS)는 아직 특정하지 않는다. A/B 수행 순서에 따른 학습효과를 줄이려면 서로 다른 순서로 비교하고 같은 난이도의 참가자 세트를 사용한다.

핵심 성공 기준: 미배정 보장 대상 누락0, 중복 배정0, 적용 전후 영향을 설명 가능, 최초 편성 완료 가능, 다른 팀의 상태를 기억에만 의존하지 않음. 속도는 정확성과 함께 비교한다. 수치 목표는 실제 A 기준을 측정한 뒤 설정한다.

## 12. 실행 단계와 현재 범위

1. **현재:** 모바일 A/B 구조와 헬퍼 전환 원칙을 문서로 비교한다.
2. **다음:** A/B에서 세터3명→센터 일부→전체 확인을 같은 샘플로 다루는 제한된 모바일 인터랙션 목업을 비교한다. 기존 position-slots를 즉시 교체하지 않는다.
3. **선택 후:** 최초18~28명 수동 편성을 완성하고 회차/초안/공개 모델과 연결한다.
4. **이후:** 한두 명 수정·실수 복구·공개 후 변경을 별도 시나리오로 기획한다.
5. **후속:** 규칙 기반 헬퍼를 연결하고, 검증된 상태·명령 위에 LLM을 붙인다.

이 문서의 B안과 개발 순서는 제안이다. 모바일 우선·최초 편성 우선·최종 헬퍼 목표는 사용자 확정 사항이다. 이번에는 코드·화면·배포를 변경하지 않았고, 모바일 A/B 성능이나 헬퍼 효과를 실제 측정하지 않았다.
