# SIDEOUT 디자인 발전안 탐색

> 최신 보충 반영: [shadcn 목업 기록](shadcn-prototype/README.md). 달력은 운동·참석 여부와 무관하게 어느 주로든 이동하며, 과거에는 실제 참석한 운동만 표시한다. 즐겨찾기 필터 옆 관리, 명단 Dialog, 세터→레프트→센터→라이트 구획, 첨부 경기 순서 예시를 별도 목업으로 구현했다. 운영 사이트는 변경하지 않았다.

> 추가 확정 요청: 명단은 홈·상세 인원 영역의 오버레이로 통합하며 명단 탭은 제거한다. 정보/공지 패널만 전환하고 하단 팀편성은 항상 유지한다. 사이드바 팀편성 메뉴를 일정 상세로 합친 제안은 [최신 목업 기록](ideation-2026-09-23/weekend/a-adaptive/README.md)의 마지막 절을 따른다.


> 최신 후속 검토: [가변 달력 비교](ideation-2026-09-23/weekend/a-adaptive/README.md). 중복 내 모임 토글 제거, 선택 결과에 맞춘 빈 행/열 축소, 즐겨찾기 모음, 인원 바 경계색 유지, 상세 중복 버튼 제거 및 주 이동/과거 기록을 검토한다. A의 기본 디자인을 유지하며 적용은 목업 범위다.


> 최신 선택: 사용자가 **A 주말 달력**을 선택했다. 후속 카드/명단/상세/내 모임 토글 발전안은 [A안 발전 기록](ideation-2026-09-23/weekend/a-refined/README.md)을 우선한다. ‘몇 명까지 몇 명’ 문구 제거 요청은 이전 부족 인원 표시 규칙보다 우선한다. 운영 사이트 적용은 아직 하지 않았다.


> 최신 후속 탐색: [주말 운동 구조 비교](ideation-2026-09-23/weekend/README.md). 사용자 추가 설명으로 총 5모임(토3·일2), 주간 고정 일정, 메뉴 통합과 달력 비교를 반영했다. **이번 비교 목업에서는 아래의 ‘모든 안에 내 모임 우선’ 조건을 날짜·시작시각순으로 대체**한다. 기존 운영 사이트의 정렬 정책은 선택 전까지 그대로다. 실제 세 모임의 시간·장소와 모든 모임의 30분 몸풀기, 경기 순서가 팀 간 대진을 뜻한다는 후속 답변도 해당 노트에 기록했다. 아래 본문은 첫 탐색 브리프의 이력이다.


2026-09-23 사용자 방향 정정. **현재 목표는 아이디어 제안과 비교이며, 최종 품질 검사는 선택·구현 후 단계다.** 이 문서는 이전 인계의 “현재 방향 안에서 확인된 결함만 수정”보다 우선한다.

## 이번에 답할 질문

현재 동작하는 SIDEOUT을 출발점으로, 일정과 신청 상태를 더 매력적이고 이해하기 쉽게 보여줄 화면 구조는 무엇인가? 현재 카드·필터·사이드바를 각각 어떻게 발전시키고 서로 어떻게 연결할 수 있는가?

오류가 있다는 증명이 있어야 아이디어를 제안할 수 있는 것은 아니다. 현재 안의 장점, 다른 구조가 열어 주는 가능성, 예상 장단점을 설명한다. 아직 시험하지 않은 효과는 가설로 표현한다.

## 유지할 것과 탐색할 것

| 유지할 제품 의미 | 발전안을 제안할 수 있는 표현 |
| --- | --- |
| 회원 소속과 탐색 필터의 구분, 내 모임 우선 | 필터 형태·위치, 그룹 구분, 일정 탐색 방식 |
| 신청·취소·공개 팀 확인 상태와 권한 | 버튼 묶음, 행동 배치, 상태 표현, 상세 열람 방식 |
| 같은 소속 명단과 공개 팀의 정보 범위 | 명단·공지·팀을 보여주는 패널/시트/모달 구성 |
| 우선 편성 보장·후보·임시 인원의 업무 규칙 | 운영자 편성 도구의 정보 위계, 목록과 코트 관계 |
| 불필요하다고 한 반복 규칙 설명 제거 | 짧은 라벨, 시각적 강조, 공간 구성으로 전달 |
| 뉴배동·히어로즈의 식별 색상과 이름 | 색의 면적·위치·강도, 배경·서체·간격·형태 |

C+B는 사용자가 좋아한 이유를 이해하는 기준점이다. 기존 카드 모양·열 수·픽셀·배치를 영구 고정하는 규칙이 아니다. 이전 A/B/C를 그대로 다시 내놓지 말고 현재 안에서 출발한 새로운 발전안을 제안한다. 새 제품 기능·정책이 필요한 아이디어는 시각적 변경과 구분해 선택 사항으로 표시한다.

## 탐색 출발점 — 최종 선택 아님

아래 세 가지는 서로 다른 구조를 탐색하기 위한 제안이다. 실제 화면과 자료를 보고 더 나은 구성으로 발전시켜도 된다.

| 발전 방향 | 핵심 아이디어와 비교할 변화 | 기대와 손해의 가설 |
| --- | --- | --- |
| 내 운동이 먼저 보이는 홈 | 기존 세로 카드를 발전시켜 내 모임의 가까운 운동에 초점. 날짜·내 상태·행동을 한 묶음으로 만들고 카드 간 강약 조정 | 다음 행동이 빠르게 보일 수 있음. 첫 카드가 지나치게 크면 다른 일정 탐색이 느려질 수 있음 |
| 여러 일정을 비교하기 쉬운 홈 | 내 모임 우선 그룹 안에서 날짜 흐름을 살린 목록 또는 주간 구성. 반복 정보 축소, 상태와 행동 정렬 | 일정이 늘어날 때 비교가 쉬울 수 있음. 모임별 개성이 약해질 수 있음 |
| 탐색과 자세히 보기를 연결한 홈 | 데스크톱 목록+상세 패널, 모바일 목록+상세 시트. 명단·공지·팀 확인의 문맥 유지 | 상세를 반복해서 열기 편할 수 있음. 한눈에 보이는 정보가 줄고 선택 단계가 늘 수 있음 |

색만 바꾼 세 버전으로 끝내지 않는다. 같은 모임·날짜·장소·인원·신청 상태로 실제 정보 배치와 행동 흐름을 비교한다. 내 모임을 먼저 보여주는 원칙은 모든 안에서 유지한다.

## 실행 과정과 스킬 역할

1. **맥락 이해:** 현재 화면을 짧게 확인해 사용자가 좋아한 부분과 발전 가능성을 파악한다. QA 점수표나 오류 목록이 첫 산출물이 되지 않게 한다.
2. **아이디어 재료:** 필요하면 실제 서비스나 디자인 사례를 조사한다. 출처와 가져올 구체적 원리(일정 비교, 선택-상세 연결, 상태 표현 등)를 남긴다. 외형만 복제하지 않는다. 자체 아이디어와 조사 결과를 구분한다.
3. **방향 제안:** frontend-design과 Impeccable의 기획·구성 탐색을 활용한다. 무엇을 발전시키는지, 화면 흐름이 어떻게 달라지는지, 장단점과 추천을 설명한다. 전면 재설계가 필요하다는 전제도 두지 않는다.
4. **비교 목업:** 다른 구조의 발전안 3개를 제안한다. 각 안은 데스크톱 구성과 모바일 대응, 신청 전/후 대표 상태를 보여준다. HTML 목업·와이어프레임·이미지 중 비교 목적에 맞게 선택한다. 정적 버튼을 실제 기능처럼 보고하지 않는다.
5. **선택·조합:** 한 안 전체 또는 각 안의 좋은 요소를 선택할 수 있게 한다. 사용자 반응을 받아 구체화한다. 탐색안을 현재 사이트에 임의 적용하지 않는다.
6. **선택 후 구현:** 선정한 구조를 실제 기능과 연결한다. 제품 규칙과 데이터 권한을 유지하고 디자인 기록을 갱신한다.
7. **마무리 검증:** Impeccable audit/polish, web-design-guidelines, 반응형·접근성·기능 검사는 선택안 구현 후 수행한다. 실험 단계에서도 기본 가독성·권한은 지키되 미세 결함 수정으로 아이디어 탐색을 대신하지 않는다.

진행 중 이미 고친 여백·포커스·버튼 조작 영역 등은 기반으로 보존한다. 기존 QA를 무효화하거나 되돌릴 필요는 없다. 이후 산출물의 우선순위를 아이디어로 전환한다.

## 탐색 단계 완료 기준

- 현재 화면에서 발전시킬 기회 3~5개: 결함 목록보다 더 나은 구조의 가능성에 집중.
- 서로 다른 구조의 발전안 3개: 설명, 화면 목업, 기대 효과와 장단점.
- 공통 콘텐츠·상태로 비교한 표와 추천안, 조합 가능한 요소.
- 참고 사례가 있으면 링크와 적용 원리. 조사하지 않은 출처를 꾸며내지 않음.
- 사용자가 선택할 수 있을 만큼 구체적인 화면. 실제 배포나 모든 테스트 통과는 이 단계 완료 조건이 아님.
