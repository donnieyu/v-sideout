# SIDEOUT 팀편성 — 목적 적합성 및 구성 대안 보고서

> 후속 사용자 결정: 모바일·최초 전체 편성이 우선이며 A/B 비교로 진행한다. 아래의 데스크톱 후보 패널 추천은 당시 분석 기록이다. 최신 비교안은 [모바일 최초 편성 A/B 검토](MOBILE_ALLOCATION_AB_REVIEW.md)를 참고한다.

2026-09-23 · 분석만 수행 / UI·제품 규칙 변경 없음

방법: 독립 평가 A(`/root/design_review`: UX·목적)와 B(`/root/access_review`: 소스·정적 탐지), 주 작업자의 별도 브라우저 재현을 종합했다. 대상은 `position-slots` 비교 목업과 기획/명세 v0.2다. 운영 앱 전체나 실제 운영자 사용성을 검증한 보고서는 아니다.

## 1. 판단

**현재 화면은 한 자리에 선수를 넣는 도구로는 발전했지만, 여러 팀의 균형과 참가자 누락을 판단하는 운영 도구로는 아직 부족하다.** 요청의 방향은 제품 목적에 맞는다. 문제는 개별 요청을 추가하면서 전체 편성 과정의 의사결정과 상태 변화가 뒤따라 정리되지 않은 데 있다.

코트·세터 위치·미배정 강조·현재 선수 표시·교대 추가는 모두 실제 작업에서 나온 요구다. 이를 없애는 것이 해법은 아니다. **운영 판단에 필요한 정보를 같은 맥락에서 보여주고, 한 행동에 하나의 결과만 연결하는 것**이 우선이다.

앞선 구현도 매번 국소적인 요청을 빠르게 반영하면서 선택/임시 배정/저장과 회원 결과까지 함께 점검하지 못했다. 이것은 사용자 요청이 많아서 생긴 문제로 돌릴 수 없다. 이후에는 개별 요소보다 대표 작업을 완료할 수 있는지를 검토해야 한다.

## 2. 사용자의 목적을 다시 정의

운영자가 해결할 문제는 다음 세 가지다.

1. **참여할 사람 결정:** 신청·대기·우선 보장·신입·임시 인원을 누락 없이 검토한다.
2. **팀 간 배분 결정:** 세터를 확보하고 포지션·인원·운영자 판단에 따른 실력 균형을 비교한다.
3. **결과 전달:** 검토한 편성만 공개하고 변경 후에도 회원이 최신 팀과 경기 순서를 알게 한다.

현재 목업은 2번의 ‘자리 채우기’에 집중한다. 누가 반드시 포함되어야 하는지, 다른 팀이 어떻게 달라지는지, 이제 공개해도 되는지에 대한 지원은 약하다. 화면에 보이는 기능 수를 늘려도 이 세 가지 판단을 지원하지 않으면 목적 적합성은 크게 높아지지 않는다.

## 4. 주요 문제 5개

### P1-01. 선택 표시와 실제 저장 대상이 다르다 — 브라우저 재현

빈 A팀 센터에서 오수빈의 `배정`을 누른 뒤 윤지호의 타일 본문만 선택했다. 화면은 윤지호를 ‘선택됨’으로 표시하고 하단에는 `윤지호 · B팀 → A팀 센터 / 오수빈 님은 미배정으로 돌아갑니다.`라고 안내했다. 그러나 저장 결과는 오수빈이었다.

코드에서 `choice`는 강조/안내, `pendingId`는 저장 대상으로 분리되어 있기 때문이다. 이는 색감 취향이 아니라 사용자가 잘못된 결과를 예상할 수 있는 동작 불일치다.

**개선:** 승인된 Q-02대로 본문 선택을 제거하고 배정 버튼으로만 임시 배정을 바꾼다. 상단 표시·영향 안내·확정 버튼은 하나의 임시 배정 상태에서 계산한다. 이번 분석에서는 수정하지 않았다.

### P1-02. 여러 팀을 보여주지만 배정 순간 비교를 가린다 — 브라우저 확인

1280×720 화면에서 A/B/C팀은 나란히 놓인다. A팀 선수 선택을 열면 중앙 520px 폭의 모달이 B팀을 가리고 보드는 어두워진다. 모달 높이는688px이었다. 팀 구성을 함께 보려는 목적과 후보 선택 단계의 화면이 서로 충돌한다.

모달 자체가 잘못된 것은 아니다. 한 자리를 정확히 수정하는 데는 적합하다. 그러나 18~28명을 처음 배정할 때 매번 열고 닫는 방식은 비교와 기억을 반복하게 한다. 이 효율 저하는 사용성 추론이며 실제 소요시간을 측정하지 않았다.

**개선:** 최소안은 Dialog 안에 출발/도착/빠지는 선수와 빈자리를 요약한다. 발전안은 넓은 화면에서 후보 패널과 팀 보드를 동시에 표시한다. 모바일은 같은 동작을 단일 선택창으로 제공해 억지로3팀을 한 화면에 줄이지 않는다.

### P1-03. 교체·이동의 부작용이 충분히 보이지 않는다 — 브라우저 확인

이미 이서준이 있는 센터에서 오수빈의 `배정`을 바로 누르면 상단은 오수빈으로 바뀌고 하단은 `오수빈 님을 배정했어요. 저장하면 반영됩니다.`라고 나온다. **이서준이 미배정으로 돌아간다는 이름 안내가 그 경로에는 없다.** 다른 팀 이동에서는 출발 자리가 비는 변화도 생긴다.

**개선:** 적용 전 변화 요약을 고정된 형식으로 계산한다.

```text
오수빈 → A팀 센터
이서준 → 미배정
(다른 팀에서 이동하면) B팀 센터 → 빈자리
```

확인창을 하나 더 띄우지 말고 현재 선택 영역 안에 표시한다. 이후 ‘맞교환’이 필요해지면 이동과 별도 명시 행동으로 검토한다. 지금 이동을 자동 맞교환으로 바꾸면 안 된다.

### P1-04. 채운 수는 보여주지만 편성 완료 여부는 판단하기 어렵다 — 코드 확인

배정17명·미배정4명만으로는 남은 사람이 보장 대상인지, 대기자인지, 별도 참여 신입인지 알 수 없다. 팀별 포지션 인원은 보이지만 실력 정보나 평가 불확실성도 없어 균형은 운영자의 기억에 의존한다. 현재 가상 후보에는 접수 시각·우선 보장·실력 데이터가 없다.

**개선:** 운영자에게만 전체 배정 상태, 미배정 신청자/대기자, 보장 누락을 구분한다. 공개를 막는 항목은 해당 인원이나 자리로 이동할 수 있게 한다. 모든 사람에게 장황한 운영 규칙을 다시 쓰는 방식은 피한다.

실력 단계가 들어오더라도 팀별 숫자 합계가 곧 공정함이라고 주장하면 안 된다. 같은 포지션의 운영자 평가·주/부 역할·미평가 인원 등 판단 근거를 먼저 보여준다. 미평가는 최하점이 아니다. 실제로 어떤 정보를 비교하는지는 운영자 검토로 확인할 필요가 있다.

### P1-05. 저장 상태가 실제로 이어지지 않는다 — 코드 확인

Dialog 저장은 편집 보드 변경이고, 상단 저장은 빈 교대 줄 정리와 성공 문구다. 별도의 저장 초안·공개본·서버 저장은 이 목업에 없다. 일정 상세 통합 목업에는 다른 구현의 초안/공개 모델이 있다. 서로 다른 목업의 장점을 하나의 완성 기능으로 설명하면 안 된다.

**개선:** 이미 결정한 Dialog 적용 / 최초 초안 저장 / 수정→저장 / 별도 공개를 상태와 함께 통합한다. 초안 편집이 회원 공개본을 바꾸지 않도록 한다. 새 UI보다 이 동작 경계를 먼저 고정하는 것이 우선이다.

현재 후보 정렬도 판단을 대신하지 않는다. 미배정 대기자가 먼저 보여도 보장 회원의 누락은 공개 단계에서 검증되어야 한다. ‘주 포지션’ 필터에 세터 예외가 들어오는 것은 현재 구현 사실이며, 고정 세터 자리 이후에도 어떤 범위를 유지할지는 명세의 미결 항목으로 남긴다.

## 5. 유지할 강점

- 세터 전용 자리와 프로필 포지션 분리: 자리 이름이 사람에 따라 바뀌지 않아 팀 비교 기준이 안정적이다.
- 현재 배정과 후보 분리, 미배정/배정됨 텍스트: 색만으로 의미를 전달하지 않는다.
- 동일 데이터의 코트/행 표현, 중복 없는 선수 이동: 이후 다른 레이아웃으로 발전시킬 기반이 있다.
- 저장과 공개를 구분하는 제품 방향: 당일 수정과 회원 정보 공개에 필요한 경계다. 포지션 목업에서는 아직 연결 과제다.

코트 표현은 배구 모임의 성격이 드러나는 요소다. 정체성을 버리고 일반 관리 표만 만들 필요는 없다. 다만 운영 편집 효율과 회원 결과의 인상은 같은 화면 밀도를 요구하지 않는다.

## 6. 구성 대안 3개

### A. 자리 중심 보드 + 영향 요약 Dialog

```text
팀편성 상태 / 저장·공개
[ A팀 코트 ] [ B팀 코트 ] [ C팀 코트 ]
자리 선택 → 후보 Dialog → 변화 요약 → 적용
```

현재 구조를 유지하면서 후보 선택 중 빠진 비교 맥락을 요약으로 보완한다. 코트/행을 유지하고 Dialog의 현재 배정·검색·하단 적용을 정리한다.

- 적합: 한두 자리 수정, 작은 화면, 기존 방식에 익숙한 운영자.
- 장점: 변화 범위가 작고 최근 결정 대부분을 바로 활용한다.
- 단점: 최초 대량 배정은 반복적인 열기/닫기가 남는다. 다른 팀 전체를 보고 판단하려면 모달을 닫아야 한다.
- 필요 작업: Q-01/Q-02 이행, 변화 요약, 보장 누락과 저장 상태 연결.

### B. 팀 비교 보드 + 유지되는 후보 패널 — 우선 비교할 추천안

```text
상태 / 초안 저장·공개
선택 자리: A팀 센터                 후보 패널
[ A팀 ] [ B팀 ] [ C팀 ]             검색 / 필터
역할별 이름·소속 / 자리             미배정 우선
코트 ↔ 행 전환                     [배정] → [적용]
                                  출발·교체 영향
```

넓은 화면은 팀 보드와 후보를 동시에 보여준다. 모달처럼 보드를 가리지 않고 공간을 배분한다. 자리 선택 방식은 유지한다. 다른 자리로 바꿀 때 미적용 변경을 조용히 버리지 않도록 적용/되돌리기 규칙이 필요하다.

행 보기는 동일 역할이 팀별 같은 높이에 놓이도록 비교용 표현을 검토한다. 큰 포지션 그룹/인원 배지는 다시 만들지 않는다. 코트 보기는 유지하며, 패널 때문에 코트가 너무 좁아지는 중간 폭에서는 A의 선택창으로 전환한다. 모바일은 A와 같은 Dialog/전체 높이 선택창이 더 현실적이다. 데이터와 적용 의미는 같다.

- 적합: 최초 편성, 여러 팀 세터/센터 비교, 마감 전 연속 수정.
- 장점: 선택 도중에도 다른 팀을 확인한다. 후보 검색 맥락을 유지하기 쉽다.
- 단점: 가로 공간이 필요하고 ‘지금 어느 자리를 편집하는가’를 항상 명확히 해야 한다. 모바일에 패널을 억지로 축소하면 오히려 복잡해진다.
- 필요 작업: 비모달 패널, 활성 자리 강조, 자리 이동 중 미적용 상태 처리, 반응형 전환.
- 범위: 레이아웃 대안이며 아직 승인·구현하지 않는다. 필수 드래그 기능은 포함하지 않는다.

### C. 포지션별 분배 흐름 + 최종 보드

```text
참가 후보 → 팀 수 → 세터 → 레프트·센터·라이트 → 교대 → 전체 비교
                         [언제든 보드로 이동]
```

‘빈 칸’보다 ‘이번에 배정할 선수 묶음’을 먼저 본다. 세터 후보를 팀들에 분산하고 다음 역할로 넘어간다. 반드시 순서를 끝내야 편집할 수 있는 마법사 형태는 피한다. 다음 자동 헬퍼의 출발점으로 적합하다.

- 적합: 빈 상태에서 처음 편성, 신규 운영자, 후속 코드 기반 헬퍼.
- 장점: 세터 우선이라는 운영 사고 순서와 맞고 반복 검색을 줄일 가능성이 있다.
- 단점: 여러 역할이 가능한 선수를 한 단계에서 소비하면 다음 포지션이 부족해질 수 있다. 대기 추가·한 명 교체에 전체 흐름을 강요하면 느리다.
- 필요 작업: 동일 회원의 복수 가용 역할, 단계 간 되돌림, 부족 인원 처리, 언제든 보드로 전환.
- 범위: 사용자가 정한 순서대로 수동 편성/결과 확정 뒤 검토한다. 지금 AI나 자동 배정을 추가하지 않는다.

| 비교 기준 | A 자리+Dialog | B 보드+후보 패널 | C 포지션별 흐름 |
|---|---|---|---|
| 최초18~28명 배정 | 반복이 많음 | 비교 맥락 유지에 유리 | 역할별 일괄 판단에 유리 |
| 한두 명 수정 | 단순함 | 빠른 연속 수정에 유리 | 보드로 빠지는 경로 필요 |
| 여러 팀 동시 비교 | 선택 중 제약 | 넓은 화면에서 가장 유리 | 마지막 보드에서 확인 |
| 모바일 | 단일 작업 집중 | 모바일 선택창으로 전환 필요 | 단계 길이·되돌림 관리 필요 |
| 최근 확정 요구 재사용 | 높음 | 높음, 레이아웃 변화 | 데이터 재사용, 흐름 변화 큼 |
| 개발·검증 부담 | 상대적으로 작음 | 중간 | 가장 큼 |
| 추천 시점 | 기준선 / 모바일 / 빠른 수정 | 다음 레이아웃 비교 후보 | 헬퍼 단계 |

이 평가는 예상 적합성이다. 시간 절약률이나 객관적인 우열을 측정한 결과가 아니다.

## 7. 추천 조합과 개발 전에 비교할 것

**단기 기준선은 A, 발전 방향은 B, 헬퍼는 이후 C**를 추천한다. 회원 결과 화면에는 코트의 장점을 남긴다. 운영 편집에서는 후보와 팀 비교가 더 중요하므로 결과 화면과 같은 밀도를 강요하지 않는다. 같은 페이지·같은 데이터이면서 편집 모드의 공간 배분은 달라질 수 있다.

현재 사용자 확정 규칙을 바꿀 필요가 없는 개선은 먼저 명세에 연결한다: 중복 선택 상태 제거, 저장 범위 분리, 변경 영향 요약, 우선 보장 누락의 공개 검증. 하지만 구현은 다음 단계다. B를 추천한다고 곧바로 패널을 추가하지 않는다.

3개 디자인 전체를 정교하게 제작하기보다, **A와 B에서 같은 참가자·같은 팀 수로 아래 작업을 비교**하면 핵심 판단을 빨리 얻을 수 있다. C는 이후 단계로 둔다.

| 과제 | 관찰할 것 | 좋은 결과 |
|---|---|---|
| 빈3팀에18명 배정 | 검색 반복·창 열기/닫기·팀 재확인·실수 | 세터와 역할별 분산을 쉽게 비교 |
| A/B의 센터 조정 | 출발 빈자리/밀려난 선수 설명 가능 여부 | 적용 전 두 팀의 변화 이해 |
|21명 중 대기자 포함 검토 | 우선 보장 누락 발견 여부 | 정렬과 편성 자격을 혼동하지 않음 |
| 휴대전화에서 한 명 교체 | 버튼 접근·스크롤·대상 기억·취소 | 다른 팀과 저장 범위를 잊지 않음 |
| 초안 저장 후 회원 결과 보기 | 공개 전 정보 노출·재공개 차이 | 회원에게는 공개본만 표시 |

예를 들어 빈자리18개를 각각 `+ → 배정 → 적용`으로 채우면 최소54개의 명시 행동이 필요하다. 검색·스크롤·교대 추가는 제외한 코드 구조상 계산이며 실제 시간 측정이 아니다. 이 수치를 줄이는 것보다 오류 없이 비교하고 수정하는지가 더 중요하다.

## 8. 지금 추가하지 않을 것

- 보기 좋은 균형 점수나 AI 공정성 수치: 평가 근거와 데이터가 아직 없다.
- 모든 포지션에 새로운 그룹/안내문/확인창: 요청한 간결함을 다시 해친다.
- 자동 맞교환: 현재 이동 의미를 바꾸며 신규 명세가 필요하다.
- 드래그만 가능한 편집: 모바일·키보드 접근과 충돌한다. 추가하더라도 버튼 대안 유지.
- 초안 변경의 자동 공개: 확정된 저장/공개 분리를 위반한다.
- 코트상의 위치를 실제 첫 로테이션으로 기록: 현재 화면의 의미를 넘어선다.

## 9. 운영자 유형에 따른 위험

숙련 운영자는 반복적인 Dialog 열기와 기억에 의존하는 팀 비교 때문에 느릴 수 있다. 새 운영자는 미배정 녹색 후보를 반드시 먼저 편성해야 할 사람으로 오해할 수 있다. 현장에서 휴대전화를 쓰는 운영자는 긴 교대 목록과 여러 저장 범위 때문에 중단 후 복귀할 때 현재 상태를 잊기 쉽다. 앞 두 경우의 사용성 영향과 모바일 중단 상황은 추론이며 실제 사용자 시험이 필요하다.

작업의 만족 지점은 선수를 한 명 넣었을 때보다 **전체 편성을 검토하고 자신 있게 공개할 때**다. 현재는 그 마지막 확인을 돕는 정보가 부족하다. 검토 완료를 돕는 짧은 상태와 공개 전 변화 확인이 장식 추가보다 효과적일 가능성이 높다.

## 10. 보조 휴리스틱 평가

0~4점의 소스/제한된 조작 기반 잠정 평가다. 실제 만족도나 제품 완성률이 아니며, 향후 같은 범위의 비교용으로만 사용한다.

| 항목 | 점수 | 근거 |
|---|---:|---|
| 상태 가시성 | 2 | 배정 표시는 있으나 선택 강조와 저장 대상 불일치 |
| 현실 언어 | 3 | 배구 역할 적합, 주 포지션 필터에 예외 포함 |
| 사용자 제어 | 2 | Dialog 취소 가능, 전체 초안 취소/되돌리기 미연결 |
| 일관성 | 2 | 공통 컴포넌트, 다른 저장 의미와 선택 상태 중첩 |
| 오류 예방 | 2 | 중복 방지, 교체 영향·보장 검증 부족 |
| 기억보다 인지 | 2 | 현재 선수 강조, 선택 순간 전체 비교 차단 |
| 효율성 | 2 | 검색·보기 전환, 반복적인 자리별 왕복 |
| 절제된 구성 | 3 | 코트에 집중, 불필요한 본문 선택 남음 |
| 오류 복구 | 1 | 지역 취소만 확인, 전체 복구·실서버 실패 대응 미구현 |
| 도움말·맥락 | 2 | 기본 조작 안내, 완료 판단 근거 부족 |
| 합계 | **21/40** | 제한된 목업 평가. 서버 실패와 실제 모바일 복구는 미검증 |

## 11. 근거와 검증 한계

- A는 기획/소스를 독립 검토했고 B 결과를 읽지 않았다. B는 A 결과를 보지 않고 정적 탐지·소스 관측을 수행했다. A 완료 후 B 상세를 합성했다.
- 양쪽 보조 검토의 브라우저 목록은 비어 접근하지 못했다. 주 작업자가 별도 숨김 탭에서1280×720 보드·Dialog·교체·선택/저장 불일치를 직접 확인했다. 사용자 탭과 데이터는 변경하지 않았고 임시 탭은 닫았다.
- 정적 탐지는 `position-board.tsx`에1회, 결과0건(exit0). CSS·동작·제품 목적이 통과했다는 뜻이 아니다. 실제 재현 문제를 탐지기가 찾지 못한 것이 모순은 아니다.
- 브라우저 detector 주입/overlay는 사용하지 않았다. read-only evaluate 정책에 따라 임의 DOM/script 주입을 하지 않았다. 별도 live-server도 시작하지 않았다.
- 최신 모바일·가상 키보드·스크린리더·실운영 속도·서버 권한은 이번에 검사하지 않았다. 기존 모델 검사52개를 이번 개선안의 통과 근거로 사용하지 않았다.
- 참고: [기획서 v0.2](TEAM_ALLOCATION_PLAN.md), [기능 명세서 v0.2](TEAM_ALLOCATION_SPEC.md), [UI 코드](shadcn-prototype/src/position-board.tsx), [모델](shadcn-prototype/src/position-board-model.ts), [스타일](shadcn-prototype/src/position-board.css).

다음 선택은 **A를 먼저 정리할지, A/B를 같은 과제로 비교할지**, 그리고 **최초 전체 편성과 경기 직전 소수 수정 중 무엇을 먼저 최적화할지**다. 이미 확정한 적용/저장·선택 방식은 다시 결정할 대상이 아니다.
