# SIDEOUT 팀편성 — 단계별 작업·검토 보고서

2026-09-23 · v1.0 · 사용자 검토용 진행 계획

진행 상태 보충(2026-09-24): **B 연속 배정을 발전시키고 A는 참고본으로 보존하는 방향이 확정되었다.** A/B 선택 단계는 종료했다. 이후 포지션별 배정을 기본으로 정하고 [B v4 모바일 화면](MOBILE_POSITION_FLOW_V4.md)에 요약 배치판과 스크롤 선수 풀을 적용했다. 자율 배치 선택지는 보류했다. 아래 작성 당시 상태표는 역사적 계획이며 저장·공개·운영 앱 통합이 완료된 것은 아니다.

## 1. 추천 순서와 이번 보고서의 의미

**모바일 A/B 체험 → 방향 선택 → 최초 전체 편성 완성 → 일정 상세·공개 결과 연결 → 한두 명 수정 흐름 → 규칙 기반 헬퍼 → LLM 확장** 순서를 제안한다. 실제 운영에 필요한 인증·서버 저장은 별도 운영 준비 단계로 관리한다.

수동 편성부터 개발한다는 방향을 유지한다. 다만 헬퍼가 사용할 조건·배정·검증·저장 구조까지 미리 고려해, 수동 화면을 완성한 다음 기반을 다시 만드는 일을 줄인다. 헬퍼의 상세 화면이나 자동 배정 기능을 지금 먼저 개발한다는 뜻은 아니다.

이 문서는 작업 순서와 판단 지점을 설명하는 보고서다. 전체 후속 기능의 일괄 승인이나 구현 완료를 의미하지 않는다. 화면 방향이 정해지면 해당 단계의 구체적인 구현 계획을 작성한다.

## 2. 현재 어디까지 정해졌는가

| 구분 | 현재 상태 |
|---|---|
| 사용자 확정 | 모바일 우선, 최초 전체 편성 우선, A/B 비교 진행, 이후 한두 명 수정 기획, 최종적으로 헬퍼와 수동 조정 연결 |
| 사용자 확정 | 선택창은 `적용`, 최초 전체 편성은 `초안 저장`, 기존 편성은 `수정 → 저장`, `공개`는 별도 |
| 사용자 확정 | 선수 타일의 `배정` 버튼으로만 임시 배정하고 X로 해제 |
| 작성된 자료 | 팀편성 기획·기능 명세·비판적 분석·모바일 A/B 구조 비교 |
| 아직 제안 | B안의 연속 배정 구조, 단계별 세부 실행 방식, 헬퍼의 조건 입력·검토 방식 |
| 아직 미완료 | 새 모바일 A/B 인터랙션 비교, 선택된 화면의 전체 흐름 구현, 통합된 저장·공개·권한 검증 |
| 운영 준비 별도 | 실제 로그인·계정 발급·서버 권한·영구 저장·동시 편집 대응 |

현재 `position-slots`는 별도의 배정 실험 화면이며, `a-shadcn` 일정 상세와 운영용 `web/` 앱은 서로 다른 구현이다. 기존 화면에 기능이 보인다는 사실을 실제 운영 앱의 통합 완료로 취급하지 않는다. 이전 검사 통과 기록도 새 설계 전체의 완료 근거로 확대하지 않는다.

## 3. 단계별로 무엇을 만들고 무엇을 판단하는가

### 1단계 — 모바일 A/B를 직접 비교한다

**목적:** 예쁜 화면을 고르는 것보다, 여러 팀을 처음부터 편성할 때 덜 헷갈리고 덜 왕복하는 방식을 찾는다.

- **A안:** 팀의 자리를 누르고 선택창에서 선수를 배정하는 방식. 코트와 자리 관계를 이해하기 쉽지만 반복해서 선택창을 열고 닫아야 한다.
- **B안:** 위쪽에 팀별 배정 요약, 아래쪽에 현재 자리의 후보를 두고 연속으로 배정하는 방식. 팀 비교와 연속 작업에 유리할 가능성이 있지만 현재 대상 팀·포지션이 명확해야 한다.
- 동일한 샘플·규칙·버튼 의미로 `빈 3팀 → 세터 3명 → 센터 2명 → 전체 확인`을 체험하게 한다.
- 360~430px 모바일 폭을 우선하고, 320px·큰 글꼴·데스크톱도 확인한다. 기존 목업은 보존하고 별도의 비교 경로를 만든다.
- 확정된 `배정/X/적용` 의미를 두 안에 동일하게 반영한다. 결과 화면의 코트/행 보기는 같은 데이터를 사용한다.

**보여드릴 결과물:** 클릭 가능한 A/B 링크, 같은 작업 지점의 모바일 화면, 작업 왕복·대상 혼동·다른 팀 비교·오류 복구에 대한 비교표와 추천.

**완료 기준:** 두 안에서 동일한 과제를 수행할 수 있고, 무엇이 다른지 사용자가 직접 확인할 수 있다. 체험하지 않은 속도 개선을 수치로 주장하지 않는다.

**사용자 결정:** 체험 후 A, B 또는 구체적인 조합을 선택한다. 현재 가설은 B가 최초 전체 편성에 유리하다는 것이지만, 아직 우승안으로 확정하지 않는다. 짧은 체험의 선택은 다음 단계 전체 인원 검증에서 재확인한다.

**승인 관계:** A/B 비교 제작은 이미 요청한 범위이므로 다시 사전 승인받지 않는다. 비교안 선택이 실제 구현 방향을 정하는 첫 번째 주요 결정이다.

### 2단계 — 선택한 방식으로 최초 전체 편성을 끝낼 수 있게 한다

**목적:** 일부 자리만 채워지는 데모에서 벗어나 처음부터 초안 저장까지 완주한다.

- 18명부터 전체 배정을 진행하고, 21·24·28명과 3·4팀, 복수 교대로 범위를 넓힌다. 이 숫자들은 테스트 사례이며 허용 인원을 고정하는 규칙이 아니다.
- 세터를 먼저 읽을 수 있는 구조와 전위 세터 자리를 유지한다. 다른 포지션부터 작업하는 것을 막지 않는다.
- 미배정 선수, 이미 배정된 선수, 신청자와 대기자를 구분한다. 다른 팀에서 선수를 이동하거나 기존 선수를 교체할 때 변경 결과를 확인할 수 있게 한다.
- 임시 배정·해제·적용·취소, 빈 교대 자리 정리, 전체 검토·초안 저장을 연결한다.
- 헬퍼도 재사용할 배정·이동·해제·검증·저장 기능을 화면과 분리한다. 자동 배정은 아직 넣지 않는다.

**보여드릴 결과물:** 전체 인원을 배정할 수 있는 모바일 화면, 인원별 시나리오 결과, 저장 전후 상태 설명, 기존 명세 대비 구현 상태표.

**완료 기준:** 중복 배정이나 알 수 없는 선수 누락 없이 최초 편성→검토→초안 저장이 가능하다. 오류를 복구할 수 있고, 미배정 우선 보장 대상이 드러난다. 모바일에서 다른 팀 상태를 기억에만 의존하지 않고 확인할 수 있다.

**사용자 검토:** 실제 전체 편성의 피로도와 이해도를 확인한다. 승인된 방향 안의 간격·정렬·버튼 크기·버그는 바로 수정한다. 구조 변경이 필요할 정도의 문제라면 해당 부분의 비교안을 제시한다.

### 3단계 — 일정 상세에서 편성과 결과를 연결한다

**목적:** 별도의 배정 실험 화면을 최종 제품 흐름에 연결한다.

- 일정 상세의 권한 있는 사용자에게 편집을 제공한다. 별도 팀편성 관리 화면을 최종 진입점으로 만들지 않는다.
- 편집 중 상태, 저장된 초안, 회원에게 공개된 결과를 분리한다. 초안 저장만으로 공개본이 바뀌지 않게 한다.
- 운영 범위, 대리 편성 예외, 우선 편성 보장, 신청자·대기자의 공개 결과 열람 조건을 연결한다.
- 회원 결과의 팀·선수·모임 표시, 코트/행 보기, 경기 대진 순서를 함께 검토한다. 프로필 평가·주/부 포지션 등 운영자 정보가 결과에 섞이지 않게 한다.
- 홈→일정 상세→편집→초안 저장→공개→회원 확인까지 하나의 흐름으로 검증한다.

**보여드릴 결과물:** 통합된 일정 상세 시연, 운영자·회원·미배정 대기자별 화면, 저장과 공개의 차이를 보여주는 사례.

**완료 기준:** 최초 전체 편성이 제품 흐름 안에서 끝나고 회원에게 올바른 공개 결과가 보인다. 공개를 막아야 하는 중복·빈 팀·우선 보장 누락이 검증된다. 목업 권한과 실제 서버 권한은 구분해 보고한다.

**사용자 결정:** 아직 미정인 공개 제한·별도 참여 인원의 공개 범위는 구체적인 사례를 보고 결정한다. 기존 확정된 권한·공개 규칙을 다시 설계하지 않는다.

### 4단계 — 그다음 한두 명 수정 흐름을 설계한다

**시작 조건:** 2~3단계에서 최초 전체 편성 흐름을 확인한 뒤 진행한다.

- 늦게 합류한 대기자 추가, 기존 선수 해제·교체, 팀 간 이동 등 실제 수정 상황을 정리한다.
- 변경 전후와 영향을 받는 선수가 보이게 하고, 수정 저장과 다시 공개하는 과정을 구분한다.
- 맞교환·일괄 이동 같은 새로운 편의 기능은 필요성이 확인된 경우에만 제안한다.

**보여드릴 결과물:** 대표 수정 사례별 전후 화면과 조작 흐름, 최초 편성 화면에서 재사용하는 부분과 추가하는 부분.

**완료 기준:** 나머지 팀을 의도치 않게 바꾸지 않고 원하는 선수를 수정하며, 저장된 초안과 기존 공개본의 차이를 이해할 수 있다.

**사용자 결정:** 구체적인 수정 흐름을 확인한 뒤 신규 동작의 구현 범위를 선택한다. 최초 편성 중의 X해제·적용 취소 등 기본 실수 복구는 이 단계까지 미루지 않는다.

### 5단계 — 실제 운영에 필요한 기반을 연결한다

**목적:** 로컬 샘플에서의 정상 동작을 실제 회원 서비스로 연결한다. UI 선택이 끝난 뒤 연결 구조를 설계하며, 실제 모임 운영 전에는 이 단계를 통과해야 한다.

- 실제 로그인과 마스터의 계정 발급, 회원 소속·운영 범위, 서버 측 권한 확인을 구현한다.
- 회차별 신청·대기·초안·공개본을 영구 저장하고 새로고침·재접속·동시 수정·저장 실패를 다룬다.
- 실제 모바일 기기의 키보드, 한 손 조작, 앱 전환·복귀를 검증한다. 브라우저 폭을 줄인 확인만으로 실기기 검증을 대체하지 않는다.

**보여드릴 결과물:** 별도의 운영 연결 구현 계획, 계정·저장·권한 검증 결과, 테스트 모임 운영 절차와 남은 제한.

**사용자 결정:** 실제 운영 시작 범위와 배포 대상은 작동하는 결과와 검증 근거가 준비된 시점에 정한다. 이 보고서만으로 배포·실회원 데이터 사용까지 승인된 것으로 처리하지 않는다.

규칙 기반 헬퍼의 샘플 실험은 이 단계 전체가 끝나기 전에도 별도로 비교할 수 있다. 다만 샘플 실험과 실제 운영 기능을 구분한다.

### 6단계 — 규칙 기반 헬퍼로 초안을 만든다

**목적:** 검증된 수동 기능 위에서 반복 배정 작업을 줄인다.

- 후보 확인→팀 수→세터 등 가용 인원·조건 선택→초안 생성→전체 검토→수동 조정→저장 흐름을 제안한다.
- 모든 질문을 순서대로 강요하지 않는다. 충분한 정보는 기본값으로 제안하고 부족하거나 충돌하는 조건을 확인한다.
- 같은 입력과 조건으로 결과를 재현할 수 있게 한다. 부족한 선수를 만들거나 우선 보장 대상을 조용히 제외하지 않는다.
- 운영자가 입력한 평가를 참고할 수 있지만 미평가와 낮은 평가를 구분한다. 실력 투표 기능은 선행 조건으로 묶지 않는다.

**보여드릴 결과물:** 먼저 헬퍼 흐름 목업과 생성 기준, 이후 선택된 기준의 작동 샘플 및 수동 작업 대비 비교.

**완료 기준:** 제약을 지킨 초안이 생성되고, 이유와 미해결 조건을 이해할 수 있으며, 기존 수동 편집에서 수정·저장할 수 있다. 빠르더라도 운영자의 수정 부담이 커지면 성공으로 보지 않는다.

**사용자 결정:** 흐름과 배정 기준을 확인한 뒤 구현 범위를 선택한다. 이미 확정된 공개·권한 규칙은 그대로 재사용한다.

### 7단계 — LLM을 대화와 조건 해석에 연결한다

**시작 조건:** 규칙 기반 헬퍼의 결과와 수동 수정 경로를 신뢰할 수 있어야 한다.

- 자연어 요청을 확인 가능한 조건과 변경안으로 변환하고, 선택 카드·현재 조건·편성 미리보기를 함께 제공한다.
- 권한·중복·우선 보장·저장·공개는 기존 코드가 검사한다. LLM이 바로 데이터베이스를 수정하거나 자동 공개하지 않는다.
- 응답 실패 시에도 선택형 헬퍼와 수동 작업이 유지되게 한다.
- 실력 월드컵은 별도 후속 기획으로 다룬다. 투표 결과를 객관적 실력으로 단정하지 않는다.

**보여드릴 결과물:** 실제 요청 예시로 만든 대화 시연, 규칙 기반 헬퍼보다 나아지는 지점, 모델·비용·전송 데이터·실패 대응을 포함한 연결안.

**사용자 결정:** 구체적인 연결안에서 사용할 데이터와 서비스 범위를 확인한 뒤 도입한다. 현재는 장기 목표이며 즉시 개발 범위가 아니다.

## 4. 남은 결정은 언제 확인하는가

지금 모든 질문을 한 번에 답할 필요는 없다. 작업 결과를 보고 판단할 수 있는 시점에, 영향을 받는 부분만 확인한다.

| 항목 | 확인 시점 | 제시할 근거와 추천 방향 |
|---|---|---|
| A/B 또는 조합 | 1단계 체험 후 | 동일 과제의 비교 결과. B 우세는 현재 가설이며 결과로 재평가 |
| Q-03 미적용 변경 중 닫기/대상 전환 | 1단계 인터랙션 검토 | 변경이 사라지는 사례와 보호 방식. 우발적인 바깥 클릭으로 작업이 버려지지 않도록 추천 |
| Q-04 센터·라이트 후보 범위 | 2단계 후보 목록 연결 전 | 고정 세터 자리와 다른 자리 후보 자격을 구분한 사례. 기존 후보 규칙을 임의로 바꾸지 않음 |
| Q-05 불완전한 팀의 공개 | 3단계 공개 연결 전 | 빈자리·인원 초과·포지션 부적합 사례. 운영 판단 안내와 공개 차단을 구분해 제시 |
| Q-06 별도 참여 인원의 회원 공개 | 3단계 결과 화면 연결 전 | 신입·임시 인원의 이름·분류가 누구에게 보이는지 화면으로 제시 |
| 수정 전용 흐름·헬퍼·LLM | 해당 단계의 구체안 작성 후 | 비교 가능한 결과와 변경 범위. 미래 기능을 지금 일괄 승인받지 않음 |

의사결정이 필요한 부분만 보류하고, 그 결정과 무관한 승인된 작업은 계속한다.

## 5. 앞으로의 보고 방식

매 작업 묶음이 끝나면 다음 순서로 보고한다.

1. **결과 먼저:** 실제 화면·체험 링크와 이번에 가능해진 작업.
2. **문제와 변화:** 무엇을 해결했고 기존 흐름과 무엇이 달라졌는지.
3. **검증 근거:** 수행한 시나리오, 발견된 문제, 확인하지 못한 항목.
4. **판단 요청:** 사용자가 선택해야 하는 부분만 옵션·장단점·추천으로 제시.
5. **다음 작업:** 선택에 따라 달라지는 범위와 별도 확인 없이 진행할 수정.

승인된 구조 안의 구현·문구 일치·접근성·오류 수정·검사는 매번 승인받지 않는다. 새 화면 방향, 기존 제품 규칙의 변경, 신규 기능 범위가 결정 대상이다. 코드 작성 순서와 테스트 명령까지 사용자에게 승인하도록 요구하지 않는다.

## 6. 바로 다음 작업 묶음

다음 구현 작업은 **1단계의 제한된 모바일 A/B 체험본 제작**이다. 두 가지 완제품을 각각 만드는 방식은 피하고, 같은 후보와 배정 로직을 공유하며 화면 방식만 비교한다.

최소 결과물은 A/B 체험 링크 두 개, 동일 지점의 모바일 화면, 비교표, 추천 조합이다. 함께 헬퍼의 최종 흐름을 한 장으로 정리해 두 안이 향후 어떻게 연결되는지만 확인한다. 여기서 헬퍼를 개발하거나 현재 사이트를 교체하지 않는다.

이번 보고서 작성에서는 화면·코드·배포를 변경하지 않았다. A/B 제작 자체는 이미 요청한 작업이므로 다시 승인받을 필요가 없고, **첫 번째 주요 선택은 체험 가능한 두 안을 본 뒤 방향을 고르는 것**이다.
